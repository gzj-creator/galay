# 06-高级主题

本页只讨论仓库当前真实具备的高级能力，以及它们在 `examples/` / `test/` / `benchmark/` 中的验证状态。

## 高级能力矩阵

| 主题 | 真实 API / 资产 | 当前验证状态 | 说明 |
|------|-----------------|--------------|------|
| SNI / Hostname | `SslEngine::set_hostname()`、`SslSocket::set_hostname()` | 已验证 | `examples/include/e2_echo.cc` 与 `test/t2_loopback.cc` 都会设置主机名 |
| CA 校验 | `load_ca_certificate()`、`set_verify_mode(Peer)` | 已验证 | `e2_echo_include` 传 `certs/ca.crt` 可校验；`T2` 为更强验证链路 |
| ALPN 协商 | `SslContext::set_alpn_protocols()`、`SslEngine::get_alpn_protocol()`、`SslSocket::get_alpn_protocol()` | 已验证 | `t3_policy` 在双端配置 `{"h2","http/1.1"}`，并断言协商结果为 `h2` |
| Session 复用 | `set_session_cache_mode()`、`set_session_timeout()`、`set_session()`、`get_session()`、`is_session_reused()` | 已验证 | `t3_policy` 复用第一次连接的 `SSL_SESSION`，第二次连接断言 `is_session_reused()==true` |
| CA 路径 | `load_ca_path()` | 已验证 | `t1_socket` 会创建带 OpenSSL hash 文件名的临时 CA 目录并验证加载成功 |
| 系统默认 CA | `use_default_ca()` | 环境依赖 API 级 | 默认信任库取决于运行环境，仓库当前没有独立跨平台 smoke target |
| TLS 版本约束 | `set_min_protocol_version()`、`set_max_protocol_version()` | 已验证 | `T1` 校验 `SSL_CTX` 原生 getter；`T3` 强制双端使用 TLS 1.2 |
| Cipher 策略 | `set_ciphers()` | 已验证 | `T1` 覆盖 setter 回归；`T3` 在 TLS 1.2 loopback 中实际使用约束后的策略 |
| TLS 1.3 CipherSuite | `set_ciphersuites()` | API 回归 | `T1` 仅验证 setter 调用成功；仓库还没有独立 TLS 1.3 E2E target |
| mTLS | `load_certificate()`、`load_private_key()`、`set_verify_mode(FailIfNoPeerCert)`；`test/certs/client.crt` / `client.key` | 资产存在，未落地 E2E | 仓库有客户端证书，但没有现成 target 走双向认证 |
| C++23 Modules | `galay-ssl/module/galay_ssl.cppm`、`galay-ssl` module file set | 条件启用 | 不导出单独模块 target |

## ALPN

真实来源：

- `galay-ssl/ssl/ssl_context.h`
- `galay-ssl/ssl/ssl_engine.h`
- `galay-ssl/async/ssl_socket.h`
- `test/t3_policy.cc`

当前仓库能确认的事实：

- `SslContext::set_alpn_protocols()` 现在会在客户端配置 advertised list，在服务端配置选择回调
- `t3_policy` 会在 client/server 两侧同时设置 `{"h2","http/1.1"}`
- `T3` 对 `SslSocket::get_alpn_protocol()` 与服务端 socket 的协商结果都断言为 `h2`

因此结论是：ALPN 已不只是“API 存在”，而是已有真实自动化 smoke target。

## Session 复用

真实来源：

- `SslContext::set_session_cache_mode()`
- `SslContext::set_session_timeout()`
- `SslEngine::set_session()` / `get_session()` / `is_session_reused()`
- `SslSocket` 对应包装方法
- `test/t3_policy.cc`

当前仓库能确认的事实：

- `t3_policy` 第一次连接会缓存 `SSL_SESSION`
- 第二次连接会在握手前调用 `SslSocket::set_session()`
- 第二次连接握手后，客户端与服务端都断言 `is_session_reused()==true`

因此文档可以把 Session 复用描述为“已有测试闭环的公开能力”，但不能把它扩展成“已有 benchmark 结论”。

## CA 路径与系统 CA

真实来源：

- `SslContext::load_ca_path()`
- `SslContext::use_default_ca()`
- `test/t1_socket.cc`

当前仓库能确认的事实：

- `t1_socket` 会构造一个符合 OpenSSL 目录命名规则的临时 CA 目录，验证 `load_ca_path()` 能真实成功
- `use_default_ca()` 是公开 API，但它依赖运行环境的默认信任库布局
- 因为不同平台的默认 trust store 差异较大，仓库当前没有把 `use_default_ca()` 写成“跨平台必过”的 smoke test

因此结论是：`load_ca_path()` 已有自动验证；`use_default_ca()` 仍应视为环境依赖能力。

## TLS 版本与 Cipher 策略

真实来源：

- `SslContext::set_min_protocol_version()`
- `SslContext::set_max_protocol_version()`
- `SslContext::set_ciphers()`
- `SslContext::set_ciphersuites()`
- `test/t1_socket.cc`
- `test/t3_policy.cc`

当前仓库能确认的事实：

- `T1` 会直接检查 `SSL_CTX_get_min_proto_version()` / `SSL_CTX_get_max_proto_version()` / `SSL_CTX_get_session_cache_mode()` / `SSL_CTX_get_timeout()`
- `T3` 强制 client/server 都走 TLS 1.2，并在受限 Cipher 策略下完成两次 loopback 连接
- `set_ciphersuites()` 目前只有 setter 级回归，没有独立 TLS 1.3 E2E target

因此结论是：TLS 版本约束与 TLS 1.2 Cipher 策略已具备真实测试闭环；TLS 1.3 CipherSuite 仍是 API 回归级覆盖。

## mTLS

仓库当前的事实边界：

- `test/certs/` 内已有 `client.crt` 与 `client.key`
- `SslVerifyMode` 里也有 `FailIfNoPeerCert`
- 但没有现成 target 把这些资产组合成双向认证的可执行示例

因此本仓对 mTLS 的状态是：

- 证书资产：有
- API 基础：有
- 已验证端到端示例：无

## 超时策略

需要特别说明：

- `SslErrorCode` 中存在 `kHandshakeTimeout` 与 `kTimeout`
- 但当前公开头中没有 `SslSocket::set_timeout()` 之类的显式超时配置接口

这意味着：

- 文档可以说“库会暴露 timeout 类错误码”
- 不能说“仓库已经提供某个公开 timeout setter 或完整超时示例”

## C++23 Modules

仓库实际行为：

- 根工程只在 `BUILD_MODULE_EXAMPLES=ON`、CMake `>= 3.28`、生成器支持模块且编译器侧模块依赖扫描可用时启用 `galay-ssl` 的 C++23 module file set
- 若扫描能力缺失（例如 macOS `AppleClang 17` + CMake `4.0.2` + `Ninja` 的常见命令行工具链组合），根工程会 warning 并自动关闭 `BUILD_MODULE_EXAMPLES`
- `examples/cpp/ssl/mcpp/*.cc` 依赖 `galay-ssl` 的 C++23 module file set
- 已安装包不会导出单独模块 target

因此推荐策略是：

- 源码树实验模块：可以
- 作为安装后稳定消费入口：当前不建议依赖单独 modules target

## 仍需你自行组合的高级能力

下面这些需求，当前更适合你基于 API 自行组合，而不是直接寻找仓库内现成 target：

- 双向证书认证（mTLS）
- `use_default_ca()` 在不同平台上的部署策略
- TLS 1.3 CipherSuite 的端到端回归
- 依赖调度器策略的超时治理

如果你需要仓库内现成可运行链路，请优先使用：

- `examples/include/e1_echo.cc`
- `examples/include/e2_echo.cc`
- `test/t2_loopback.cc`
- `test/t3_policy.cc`

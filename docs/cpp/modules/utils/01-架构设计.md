# 01-架构设计

本页描述当前仓库实际导出的入口、目录职责与依赖边界。

## 1. 导出面

| 入口 | 真实文件 / target | 说明 |
|---|---|---|
| 细粒度头文件 | `galay-utils/<module>/*.hpp` | 最稳妥的接入面，依赖边界最清晰 |
| umbrella header | `galay-utils/galay_utils.hpp` | 聚合公开工具，包括 `resilience/rate_limiter.hpp` |
| CMake 库 | target `galay-utils` / alias `galay::utils` | 导出 include 目录、concurrentqueue 依赖与平台链接要求 |
| C++23 模块 | `galay-utils/module/galay_utils.cppm` / `galay-utils` module file set | 仅在工具链满足条件时启用 |

## 2. 目录职责

| 路径 | 角色 |
|---|---|
| `galay-utils/` | 公开头文件与模块接口 |
| `galay-utils/core/` | 字符串、随机数、时间、类型名等纯工具 |
| `galay-utils/system/` | 系统信息、文件系统、进程、环境变量、CPU/NUMA、信号与堆栈 |
| `galay-utils/buffer/` | 字节容器、字节队列视图与字节/typed 环形缓冲 |
| `galay-utils/cache/` | 带淘汰策略的 LRU 缓存 |
| `galay-utils/concurrency/` | 线程池、任务等待器与支持并发访问的对象池 |
| `galay-utils/resilience/` | 限流器与熔断器 |
| `galay-utils/algorithm/` | 一致性哈希、MurmurHash3、负载选择、布隆过滤器、Trie 与 MVCC |
| `galay-utils/app/`、`galay-utils/config/` | CLI 与配置解析 |
| `galay-utils/encoding/` | Base64 与 Huffman 编解码 |
| `galay-utils/crypto/` | SHA1、MD5、HMAC、PBKDF2 与盐值生成 |
| `examples/` | 真实可构建示例；当前提供 `E1-BasicUsage`，满足模块条件时额外提供 `E1-BasicUsageImport` |
| `test/` | 真实断言与模块烟雾测试 |
| `docs/` | 人类可读文档；当与源码冲突时优先级最低 |
| `cmake/option.cmake` | 平台 IO 后端与构建选项 |

`system/env.hpp` 操作进程环境变量；`config/env.hpp` 解析 `.env` 文件，分别按系统接口和配置格式归类。公开类型仍位于 `galay::utils`，总头与 `galay.utils` 模块统一导出；旧目录不保留转发头。

## 3. 依赖边界

### 3.1 CMake target 级别

- `galay-utils` 通过 `galay::utils` 链接，并公开传递 concurrentqueue 依赖
- Unix 下自动附带 `pthread`
- Linux 下额外附带 `dl`

### 3.2 头文件级别

- 大多数模块只依赖标准库或平台系统头
- `galay-utils/resilience/rate_limiter.hpp` 仅依赖标准库，提供无锁同步非阻塞 `tryAcquire` 路径
- `galay-utils/galay_utils.hpp` 包含 `resilience/rate_limiter.hpp`
- `galay-utils/module/galay_utils.cppm` 导出同一套公开头文件

结论：

- “限流器不再把 `galay-kernel` 依赖带入 `galay-utils`”
- “只想用轻量模块时，细粒度头文件仍然是最稳妥的边界”

## 4. 构建开关

| 选项 | 默认值 | 真实行为 |
|---|---|---|
| `BUILD_EXAMPLES` | `ON` | 构建 `examples/CMakeLists.txt` 中的 target |
| `BUILD_TESTING` | `OFF` | 开启后构建按模块分组的 `*_test`，并在满足条件时构建 `test_import_smoke` |
| `BUILD_TESTS` | 兼容别名 | 传入时会映射到 `BUILD_TESTING` |
| `BUILD_MODULE_TESTS` | `OFF` | 显式开启后才会构建模块 target、模块示例和模块烟雾测试 |
| `DISABLE_IOURING` | `ON` | Linux 默认走 `epoll`；显式关闭后才尝试 `io_uring` |

## 5. 验证资产

| 资产 | 真实文件 | 作用 |
|---|---|---|
| 示例 | `examples/include/e1_basic.cpp`、`examples/cpp/utils/mcpp/e1_basic_usage.cc` | 覆盖 include 与 import 两条基础接入路径 |
| 功能测试 | `test/<area>/*_test.cpp` | 按模块组拆分的行为校验基线 |
| 模块烟雾测试 | `test/import_smoke.cpp` | `import galay.utils;` 的最小验证 |

## 6. 平台与特性边界

- `BackTrace` 只在 Apple/Linux 上提供实际栈采集逻辑
- `Process::daemonize()` 仅对 POSIX 语义有意义
- `SignalHandler` 修改的是进程级信号处理器
- 模块构建不支持 `AppleClang`

## 7. 当前权衡

- 仓库同时提供“细粒度头文件”和“全量 umbrella header”，但后者的依赖边界更宽
- benchmark 通过 `BUILD_BENCHMARKS=ON` 显式开启，默认不进入普通构建或 CTest
- `examples/` 当前覆盖 include/import 两条基础接入路径；更深的边界与异常路径来自 `test/<area>/*_test.cpp`

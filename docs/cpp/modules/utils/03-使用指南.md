# 03-使用指南

本页做“怎么选模块”的决策说明，不承担示例代码真相来源。真实可运行示例请看 [04-示例代码](04-示例代码.md)。

## 1. 先选头文件策略

| 场景 | 推荐做法 | 原因 |
|---|---|---|
| 只需要少量工具类 | 直接包含具体头文件 | 依赖边界最小 |
| 想快速接入常用模块 | 可以使用 `galay-utils/galay_utils.hpp` | 接入简单，且不再默认拉入限流器依赖 |
| 需要限流器家族 | 直接包含 `galay-utils/resilience/rate_limiter.hpp` | 无锁同步非阻塞接口，无 `galay-kernel` 依赖 |
| 已具备模块工具链 | 使用 `import galay.utils;` | 导入体验更好，但约束最多 |

## 3. RateLimiter 怎么选

| 类型 | 更适合什么 | 备注 |
|---|---|---|
| `CountingSemaphore` | 控制并发数量 | API 最直接 |
| `TokenBucketLimiter` | 接口限流且允许突发 | 适合通用配额 |
| `SlidingWindowLimiter` | 更接近固定时间窗配额 | 无参数化 `acquire` |
| `LeakyBucketLimiter` | 流量整形 | 更强调平滑流出 |

注意：

- 这四个类型都定义在 `galay-utils/resilience/rate_limiter.hpp`
- 仅提供无锁同步非阻塞 `tryAcquire` 路径，未通过限流时直接返回 `false`
- 不再提供协程 `acquire()` awaitable；协程等待、重试、超时策略应放在上层项目自行适配

## 4. LoadBalancer 怎么选

| 类型 | 推荐场景 | 并发提示 |
|---|---|---|
| `RoundRobinLoadBalancer<T>` | 节点能力接近、节点集大多固定 | 仅 `select()` 在节点集合不再变更时适合并发共享；并发 `append()` 需外部同步 |
| `WeightRoundRobinLoadBalancer<T>` | 需要平滑按权重分配 | 内部状态可变，外部自行同步 |
| `RandomLoadBalancer<T>` | 随机分配即可 | 内部 RNG 无锁，外部自行同步 |
| `WeightedRandomLoadBalancer<T>` | 按权重随机 | 内部 RNG 无锁，外部自行同步 |

以上并发说明是基于当前 `balancer.inl` 实现得出的结论。

补充：

- 四个 `select()` 都返回 `std::optional<T>` 按值，因此这里不是零拷贝 API

## 5. BloomFilter 怎么用

| 判断结果 | 含义 | 后续动作 |
|---|---|---|
| `possiblyContains(x) == false` | 一定不存在 | 可以直接过滤掉 |
| `possiblyContains(x) == true` | 可能存在，可能是假阳性 | 需要精确结果时回源确认 |

注意：

- `BloomFilter` 不提供 `contains()`，避免误导成精确集合。
- 不支持删除；需要删除能力时应选择 Counting Bloom Filter 或精确集合。
- false positive rate 取决于容量、插入量和 hash 分布；插入超出预期会明显提高误判率。

## 6. Pool / Thread 怎么选

| 需求 | 推荐模块 | 备注 |
|---|---|---|
| 异步执行很多小任务 | `ThreadPool` | `waitAll()` 会阻塞线程 |
| 等待一批异步工作 | `TaskWaiter` | `wait()` / `waitFor()` 会阻塞线程 |
| 非阻塞对象复用 | `ObjectPool<T>` | 池空时按需创建新对象 |
| 池空时必须等待 | `BlockingObjectPool<T>` | `acquire()` / `tryAcquireFor()` 会阻塞线程 |

## 7. Parser / App 怎么选

| 需求 | 推荐模块 | 备注 |
|---|---|---|
| 解析 `.conf` | `ConfigParser` | 支持 section 与 `section.key` |
| 解析 `.ini` | `IniParser` | 行为与 `ConfigParser` 对齐，保留独立类型 |
| 解析 `.env` | `EnvParser` | 面向 `KEY=VALUE` |
| 解析 `.toml` | `TomlParser` | 支持基础 section、dotted key 和数组 |
| 根据扩展名选择解析器 | `ParserManager` | 默认识别 `.conf` / `.ini` / `.env` / `.toml` |
| 构建带子命令 CLI | `App` / `Cmd` / `Opt<T>` | 类型安全取值、变量绑定、`--no-flag`、`--` 终止符、重复参数、候选校验、多级子命令 |

```cpp
using namespace galay::utils;

App app{"mytool", "示例工具"};
app.version("1.0.0");

auto& port = app.opt<int>("port", 'p', "监听端口").def(8080);
auto& tags = app.opt<std::string>("tag", 't', "标签，可重复").multi();
auto& verbose = app.flag("verbose", 'v', "详细日志");
auto& input = app.pos<std::string>("input", "输入文件").required();

app.on([&](Cmd&) {
    serve(port.value(), input.value(), verbose.value(), tags.values());
    return 0;
});

return app.run(argc, argv);
```

也可以把解析结果直接绑到已有变量，回调里无需再取值：

```cpp
int port = 8080;
bool verbose = false;
app.opt<int>("port", 'p', "监听端口").def(8080).bind(&port);
app.flag("verbose", 'v', "详细日志").bind(&verbose);
```

## 8. 进程优先级与 CPU 亲和性

```cpp
using namespace galay::utils;

auto priority = Process::priority();
if (!priority) {
    // processPriorityErrorString(priority.error())
}

auto cpus = Process::cpuAffinity();
if (cpus && !cpus->empty()) {
    std::array<unsigned int, 1> selected{cpus->front()};
    auto affinity = Process::setCpuAffinity(selected);
    if (!affinity) {
        // processAffinityErrorString(affinity.error())
    }
}
```

- priority 使用 POSIX nice 值语义，范围 `[-20, 19]`，数值越小优先级越高。
- 降低 nice 值通常需要额外权限。
- CPU affinity 使用零基逻辑 CPU ID；不支持的平台返回 `ProcessAffinityError::Unsupported`。
- Linux 的 `Process` 接口操作传入 pid/tid 对应线程，默认 pid 是进程主线程；不会遍历所有已有线程。需要设置调用线程时使用 `CPU::bindCurrentThread()`。Windows 保留现有进程 mask 接口及单处理器组的 `DWORD_PTR` 容量限制。
- 调用方必须检查 `std::expected` 结果，不得忽略失败。

## 9. CPU 数量、NUMA 拓扑与内存策略

先决定需要哪种信息：

| 问题 | 接口 | 使用方式 |
|---|---|---|
| 标准库建议使用多大硬件并发度？ | `CPU::count()` | 保留 `hardware_concurrency()` 提示，可能为 0；可作为线程数推导的输入 |
| 系统有哪些在线 CPU？ | `CPU::onlineCpus()` | 读取系统在线 ID 集合，不受当前线程 cpuset 过滤 |
| 当前线程实际可在哪些 CPU 上运行？ | `CPU::cpuAffinity()` | 检查成功后用 `.size()` 得到有效集合数量，从集合中选择 ID |
| 此刻正在运行在哪个 CPU？ | `CPU::currentId()` | 瞬时快照，仅用于观测；要限制后续运行位置须设置 affinity |
| 系统有哪些在线 NUMA 节点？ | `Numa::onlineNodes()` | 拓扑快照，包含当前 cpuset 可能不允许使用的节点 |
| 当前 cpuset 允许哪些内存节点？ | `Numa::allowedNumaNodes()` | 配置内存策略前检查，不能用系统在线节点代替 |
| CPU 和节点如何对应？ | `Numa::nodeOfCpu(cpu)` / `cpusOfNode(node)` | 在线 CPU 与节点关系；无 CPU 的内存节点可返回空集 |
| 两个节点的相对访问距离？ | `Numa::distance(from, to)` | 正整数相对距离，不是纳秒，也不保证对称；单节点机器只需查询自身 |
| 系统基础页有多大？ | `Memory::pageSize()` | 正数，单位字节；不是 huge page 大小 |

CPU ID 和 NUMA 节点 ID 都可能不连续。集合 `{0, 2}` 的数量是 2，不会使 ID 2 非法；按线程索引放置时从集合中取值，禁止使用 `id < CPU::count()` 校验。`CPU::count()` 不改成 affinity 数量，已有线程池并发度推导不因此改变。Linux CPU mask 已改为动态探测，支持超过 CPU 1023 的实际 ID；旧的固定上界常量已经移除，实际支持范围为 `[0, INT_MAX)`，还受内核和内存分配约束。

`Numa` 只负责拓扑和允许集合，内存策略设置/恢复由 `Memory` 提供。CPU 绑定不会自动设置内存节点，内存策略不会自动绑 CPU；通常先在启动线程中查询拓扑、选择允许集合，再配置并创建工作线程。拓扑会同步读取 sysfs，适合启动或诊断，避免在协程热路径反复调用。所有结果都是快照，跨调用遇到热插拔或 cpuset 变化时需要检查新结果。

需要临时改变策略时，保存 `PolicyState` 并使用 `restoreNumaPolicy()` 恢复，不能把原生 mode 强制转成只支持三种模式的 `Policy` 枚举：

```cpp
std::expected<void, std::error_code> runWork();

std::expected<void, std::error_code>
runWithInterleave(std::span<const unsigned> allowedNodes)
{
    using galay::utils::Memory;
    const auto saved = Memory::numaPolicy();
    if (!saved) {
        return std::unexpected(saved.error());
    }
    const auto changed = Memory::setNumaPolicy(Memory::Policy::Interleave, allowedNodes);
    if (!changed) {
        return std::unexpected(changed.error());
    }
    const auto work = runWork();
    const auto restored = Memory::restoreNumaPolicy(*saved);
    if (!restored) {
        return std::unexpected(restored.error());
    }
    return work;
}
```

`Default` / 原生 `Local` 要求空节点集；`Bind` / `Interleave` 要求非空集。原生 `Preferred` 可以指定节点，也可以使用不带 static/relative flags 的空集；空集在 Linux 回读为 `Local`。恢复保留 `MPOL_F_STATIC_NODES`、`MPOL_F_RELATIVE_NODES` 等原生 flags，relative 模式保存的是相对 cpuset 索引。恢复时 cpuset 或节点状态变化、内核不支持 flags、权限不足都可能失败；示例优先传播恢复错误，并在恢复成功时传播工作结果。

内存策略只影响后续新页分配/首次触碰，不迁移已有页，不覆盖显式 VMA 策略。新建 Linux 线程继承创建者当时的 affinity 和内存策略，已有线程不自动改变。枚举设置接口仍只提供 `Default` / `Bind` / `Interleave`；更多原生模式用于状态恢复，其支持性由编译头文件和运行内核共同决定。

Linux 的拓扑/策略错误保留 errno，缺失 sysfs 为 `ENOENT`，非法参数为 `invalid_argument`，列表容量越界/数字溢出分别为 `value_too_large` / `result_out_of_range`。NUMA 节点 mask 仍固定为 1024 位（节点 0–1023），超过容量明确失败，不能截断。CPU/NUMA 控制和拓扑在非 Linux 平台返回 `operation_not_supported`；页大小在 Linux/macOS/Windows 可查询，POSIX 系统错误保留 errno，非正数且无 errno 为 `io_error`。

暂不提供泛化的 `Memory::info()`：系统可用内存、cgroup 限额和进程 RSS 不是同一指标，后续须分别明确作用范围和单位。

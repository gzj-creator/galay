# PostgreSQL 性能测试报告（2026-08-10）

## 结论

在本机 PostgreSQL 16.14 环回实例上，Galay 与 libpq 的 simple query 吞吐在
`1/8` 并发基本相同；在 `32/64` 并发时 Galay 的三次中位吞吐分别高 `3.8%` 与
`2.9%`。prepared execute 的三次中位吞吐在 `1/8/32/64` 并发下分别高
`3.9%/0.0%/5.2%/10.2%`。所有比较请求均成功，不能把这些环回结果外推为远程网络、TLS、
写入或业务 SQL 的通用结论。

连接池热路径在单 IO scheduler 下于 pool `4-8` 个连接附近达到约 `5.1k-5.4k QPS`；
继续扩至 32 连接的收益很小，而更小池会体现为预期的 acquire 排队延迟。

## 环境与口径

- 日期：2026-08-10；Linux 7.0.0-28-generic，12 个可用逻辑 CPU（Intel Core i7-14700K）。
- 构建：`linux-perf-release`，GCC 14.2.0、CMake 3.28.3、`RelWithDebInfo`、
  `-O2 -g -DNDEBUG -fno-omit-frame-pointer`。
- 服务端：PostgreSQL 16.14，`127.0.0.1:55432`，`max_connections=100`，
  `shared_buffers=128MB`，`synchronous_commit=on`，`fsync=on`，`jit=on`。
- 每次运行以 `taskset -c 0-11` 限定到相同 CPU 集合，不与另一 benchmark 并发执行。
- Simple Query：每 client 一个同步 TCP 连接，`SELECT 1`，每 client 32 次预热；连接和
  预热不计时，worker barrier 后同时起跑。Galay 和 libpq 都显式启用 `TCP_NODELAY`，均解析
  返回值并累计响应字节。
- Prepared：同一并发和预热模型，计时前完成 `SELECT $1::bigint` 的 prepare；两端均验证返回值。
- 每个 `1/8/32/64` 并发档运行三次，并交替 Galay/libpq 的先后顺序。下表 QPS 为三次中位数；
  延迟也是三次中位数的 p50/p95/p99，不使用单次峰值。

## DataRow Parse

以下数据于 2026-08-11 复核；端到端对比表仍采用报告初版的三次中位数口径。

`benchmark_postgres_datarow_parse 100000 12 64` 使用 12 列、64-byte text value、2 个 NULL
列和 2 个空列；每次有 10k warmup，并在同一 CPU 集合连续运行 7 次。owned parse 的原始吞吐为
`2.26/2.59/2.66/2.67/2.73/2.78/2.79M rows/s`，中位数为 `2.67M rows/s`（`375.21 ns/row`）；
borrowed view 为 `5.43/5.61/5.69/6.55/6.90/7.20/7.60M rows/s`，中位数为 `6.55M rows/s`
（`152.62 ns/row`）。逐次 view/owned 比值的中位数为 `2.40x`，范围 `2.14x-2.72x`。这是本地
hot payload 微基准，仍会受频率与调度噪声影响，不能与数据库端到端 QPS 混为一谈。

## 覆盖与限制

真实 PostgreSQL CTest 覆盖 C ABI、同步/异步 simple query、prepared、事务、pipeline、pool 和
错误后连接复用；压力基准覆盖 simple、prepared、pool 与 DataRow parse。pipeline 的真实实例功能
测试已通过，但当前 benchmark 集合没有独立 pipeline 吞吐对照。

本机没有可供 CMake 使用的 Ninja（安装 `ninja-build` 因容器无 apt 写权限失败），因此 CMake 的
module file set target 不能启用；不过 GCC 14.2 直接编译 facade 与现有 `import/e1_query.cc` 已通过，
并生成 `galay.postgres.gcm`。该直接验证把源和头复制到 ASCII 临时路径：GCC 默认 module mapper
在当前含非 ASCII 路径的工作区无法翻译 include，故当前路径下的 CMake module 消费仍待 Ninja 可用后
复验。完整跨机器性能比较仍应固定 CPU frequency、服务端数据集、连接数和运行时环境，并增加远程网络、
写入 SQL、TLS 与 pipeline workload。

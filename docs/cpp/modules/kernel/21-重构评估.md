# 重构评估与 API 命名

评估日期：2026-10-07。评估对象是根目录 `REFACTOR_PLAN.md`、`REFACTOR_SUMMARY.md`
和当前生产代码，而非仅依据旧文档的完成标记。本轮不承诺任何吞吐或延迟收益。

## 优化取舍

| 旧建议 | 当前实现与收益 | 决定 |
| --- | --- | --- |
| Scheduler 配置模板化 | 已有 `IOSchedulerConfig`、默认/高吞吐/低延迟预设和三个 `*SchedulerT<Config>`。配置在构造时传入共享后端，提供编译期范围检查和不同实例容量，不特化事件循环 | 已完成，保留 |
| 迁移测试/示例 | `t192_scheduler_config.cc` 对四种配置检查启动、Task 继续、IO、timeout、重启及 `Scheduler*` 借用；CMake 另编译两组预设宏，e13 include/mcpp 示例成对存在 | 已完成，复跑 |
| 将 expected 改成错误码/out 参数 | Reactor `add_*` 已返回 `int`；`start()` 不属于逐次 IO 热路径。awaitable 的标量 expected 平凡析构，未发现结果存储瓶颈的 profile 或有效 A/B 数据 | 不实施 |
| 提取 Reactor 公共逻辑 | 已有 `IOSchedulerBase<Derived, Reactor>`、`SchedulerCore`、统一 `sched_loop.hpp`；backend 仅保留 poll/flush 与真实平台注册语义 | 已完成，不增加插件层 |
| Timer 全面模板化 | `TimingWheelTimerManager` 的 tick 可构造时设置，`replace_timer_manager` 可在启动前替换管理器 | 不实施，现有扩展满足需要 |
| 并行调度器配置/同步策略 | `ParallelSchedulerConfig` 仅声明，无生产消费点；不等于并行队列已可配置 | 不为了抽象而扩大 Runtime/并行 API |
| 删除 benchmark 结果、清理历史 | 原始结果不进入本次提交，现有忽略规则保留 | 不再重写历史或强推 |

### 不能推出 5-15% 收益

`GALAY_SCHEDULER_*` 宏本身已是编译期常量。当前模板包装只给共享后端构造器传入
容量，`EpollReactor::poll` 仍使用 `m_max_events`，共享 loop 仍读取批量预算。
因此“用了模板便能保证循环展开/吞吐提升”不成立。预设名称表示容量选择，不是 benchmark
承诺；更大的批次可能改变吞吐/尾延迟权衡，必须在实际负载上测量。

对本轮 GCC 14 / libstdc++ / x86_64 类型检查，`IOError` 为 8 字节，
`std::expected<size_t, IOError>` 与 `std::expected<void, IOError>` 各为 16 字节，
两种结果均平凡析构。对应回归是 `t197_api_naming.cc`；尺寸是当前工具链观察，不是跨平台 ABI
保证。`std::expected` 并不要求借助 `std::variant`，也不因包装标量就分配堆内存。
WG21 P0323R12 的 5.7 节明确要求 value/error 位于 expected 对象自身存储中；
该约束不代表其中的 `std::string` 等成员自己永远不会分配。
不能仅统计出现次数推导热路径成本，更不能把自行构造的错误码 microbenchmark
当成真实协程、系统调用和超时链路收益。

旧草案还有语义问题：`IOError(kDisconnectError, 0).code()` 等于零，零值不能作为统一
“无错误”哨兵。改为原始错误表示必须额外保留成功标签、错误种类、系统 errno、完成
状态及所有权语义。没有实测瓶颈，不引入第二套传播协议。

## 命名迁移

范围是 Galay 自有函数，包括公开/私有成员、静态/模板方法、自由函数、内部 helper 和
命名回调。同步生产源码、C/C++ 桥接、测试、示例、benchmark、模块消费和当前使用文档；
类型名称、C API 模块前缀、协议键名与稳定错误字符串不随函数名迁移。

| 原名 | 新名 |
| --- | --- |
| `Runtime::getNextIOScheduler` | `Runtime::get_next_io_scheduler` |
| `Runtime::blockOnIO` | `Runtime::block_on_io` |
| `RuntimeBuilder::ioSchedulerCount` | `RuntimeBuilder::io_scheduler_count` |
| `HttpRouter::addHandler` | `HttpRouter::add_handler` |
| `HttpServer::isRunning` | `HttpServer::is_running` |
| `HttpRequest::bodyStr` | `HttpRequest::body_str` |
| `HandleOption::handleNonBlock` | `HandleOption::handle_non_block` |
| `Base64Util::Base64Encode` | `Base64Util::base64_encode` |
| `PipelineOp::Put` | `PipelineOp::put` |
| `Deadline::timePoint` | `Deadline::deadline_time` |
| `BlackListConfig::clientKeyMode` | `BlackListConfig::set_client_key_mode` |
| `BlackListConfig::excludeIps` | `BlackListConfig::set_exclude_ips` |

不保留旧名别名、兼容包装或 fallback。消费者须修改源码并重新编译，旧共享库 ABI
也不能直接混用。按用户指定的小/中版本范围发布中版本，而不是把这次源码不兼容的
命名迁移伪装成小修补。这里的原名只用于迁移对照，不是继续支持的接口。

标准 coroutine 的 `await_ready`、`await_suspend`、`await_resume`、`promise_type` 等
以及第三方/外部契约保持原名。serde、concurrentqueue、OpenSSL、Swagger UI 不做命名
迁移；历史 release 记录和原始性能数据不改写。

## 验证

迁移前，API 九项以及 kernel 配置/Task 结果、HTTP 错误传播、utils cache 共 13 项
回归通过。新命名回归迁移前按预期编译失败，验证它确实区分新旧 API。

本轮实际验证环境为 Linux x86_64、GCC 14、C++23、Release 共享库及 epoll。
全量构建启用所有模块、可选 API、C ABI、示例、benchmark 和 RPC 的 etcd 接入；
CMake 原生模块开关关闭，模块消费另由 mcpp/LLVM 22.1.8 验证。

- 全量 CMake 构建通过；最终串行 CTest 共 642 项：601 通过、36 跳过、5 禁用、
  0 失败。跳过和禁用项不计为通过。
- io_uring 定向回归 6/6 通过，没有跳过：配置、新命名、accept 生命周期及文件移动。
- ASan/UBSan/泄漏检查 16/16 通过：API 九项、kernel 五项、HTTP 两项。
- mcpp `full` Release 原生模块构建通过，21 个回归程序中 19 通过、2 个后端条件
  跳过；`full` 不包含可选 API，不能据此声称 API 原生模块组合通过。
- 14 个模块 prelude 校验通过；语法树审计未发现 Galay 自有非蛇形函数声明或命名
  lambda 回调，生产类型声明、协议/错误字符串保持不变，没有新增异常。
- API 安装后移动前缀的消费者 3/3 通过；最终全量回归再次覆盖配置、安装及风格审计。

全量回归还暴露两个既有测试问题。安装消费者文件不符合 `tNN_<scenario>.cc` 规则，
改名并同步构建入口。API policy 的 procfs 线程基线会包含上一 Runtime 正在退出的
线程，迁移前的 sanitizer 二进制也能复现；仅在捕获下一场景基线前等待单线程状态，
启动/安装后的资源比较仍立即执行，保留全部副作用断言。修复后开启泄漏检查连续
30 次通过，不用反复运行挑选一次成功结果作为验收。

最后一轮并行全量回归中，`rpc.t30.deadline.cancel` 曾因 PID 派生端口被占用而在
bind 返回 `EADDRINUSE`，当轮为 600 通过、36 跳过、5 禁用、1 失败。该用例随后连续
20 次通过；最终完整串行重跑得到上述 601/36/5/0，不能把前一轮记成全部通过。
本轮不扩张 RPC server 的端口 API，既有测试的固定端口碰撞风险仍需注意。

未实跑 Bazel、原生 macOS/BSD kqueue、Windows 或所有后端与链接方式的笛卡尔积；
外部数据库/集群门控测试保持跳过，不改动现有服务。本轮不重新运行性能对比，
编译和单测成功不代表吞吐或延迟改善。

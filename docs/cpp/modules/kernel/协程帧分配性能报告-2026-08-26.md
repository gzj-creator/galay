# C++ 协程帧分配优化性能评审

**评审日期:** 2026-08-26

**评审对象:** `624b2d8`（合并提交；协程实现来自 `e474dbe`）

**对照基线:** `0e24a32`（`e474dbe^`）
**范围:** `TaskPromise<T>` / `TaskPromise<void>` 的 coroutine frame recycler、TaskState 生命周期和相关调度路径。C 协程帧不在本次范围内。

## 后续优化复核（2026-08-27）

在原始结果基础上，当前实现已完成以下调整：

1. 完成态 `TaskState` 销毁使用 teardown-only fast path；未提交 frame 仍保留显式销毁保护。
2. 普通对齐 frame 改为 headerless size-class block；sized delete 按编译器提供的 frame size 回收，超对齐 block 保留 provenance header，unsized ordinary delete 直接释放。
3. 移除生产库中的 allocator test hooks 和测试查询 API；A/B baseline 改为 benchmark 内部的 direct `new/delete`。
4. promise 内部使用非拥有 `TaskState*`，保留兼容性的 `TaskRef` view，减少热路径 borrowed-tag 解码。
5. 保持 `TaskState` 128-byte footprint，集中 ownership/admission flags，并将 frame/TaskState TLS cache 上限由每桶 1,024 降为 256。

当前 Release/epoll 串行复核中，`b34` 的完成任务路径约为 `60~66 ns/op`；普通 frame recycler 约为 `12~13 ns/op`，direct malloc baseline 约为 `10~12 ns/op`。因此 recycler 的主要价值仍是减少长期分配压力和稳定驻留内存，而非在 glibc tcache 下保证单次分配绝对更快。

新增 `b35_coroutine_task_scale` 支持 `churn/live` 两种规模压力：当前已验证 `5,000 万` 次累计完成任务，以及 `1,000 万` 个同时存活的初始挂起任务；后者最大 RSS 约 `3.06 GiB`。该 benchmark 不接入 scheduler、timer 或真实 I/O，不能替代运行时宏基准。

> The sections below preserve the original `624b2d8` measurements for comparison; the
> current implementation and acceptance status are summarized in the follow-up section above.

## 原始结论（历史数据）

这次提交同时包含一个明确的生命周期修复和一个尚未达到整体采用门槛的分配器优化：

1. **同线程固定尺寸 frame churn 有微基准收益。** 256-byte size class 的 recycler 相对同一实现中关闭 recycler 的路径，p50 从 `23.62 ns` 降到 `14.06 ns`（-40.5%，约 `42.34M -> 71.12M ops/s`，+68.0%），p90 从 `28.70 ns` 降到 `16.44 ns`（-42.7%），p99 从 `34.51 ns` 降到 `23.97 ns`（-30.5%）。预热后 fallback 估计为 `0`，关闭 recycler 时为每次 `20,000` 次。
2. **常见的完成任务路径出现回退。** 在相同编译器和 epoll 配置下，`Task<void>` 创建、恢复、完成、销毁的 p50 从 `83.357 ns` 变为 `87.678 ns`（+5.18%），p90 从 `93.872 ns` 变为 `99.744 ns`（+6.26%），p99 从 `100.632 ns` 变为 `107.691 ns`（+7.01%）。这超过 kernel 核心基准当前 `5%` 的回退容忍线，不能把 recycler 宣称为无条件的端到端性能提升。
3. **未提交任务的帧泄漏被修复。** 一百万次只创建后丢弃、从不恢复的任务，基线峰值 RSS 为 `191,288 KiB`，新实现为 `3,828 KiB`（-98.0%）；一次运行的 wall time 从 `0.33 s` 降到 `0.15 s`。这首先是生命周期正确性收益，不能与 recycler 的纯分配收益混为一谈。

原始结论仍用于解释 `624b2d8` 的历史数据；后续优化的最终采纳应以当前 `b34` 完成任务路径、真实 scheduler/I/O workload 和长期 RSS 复测为准。

## 测量方法

- `benchmark/cpp/kernel/b34_coroutine_frame_allocator_pressure.cc`：每个进程内部先 warmup `2,000` 次，再测 `20,000` 次；同一二进制绑 CPU 0 重复采样，报告 p50/p90/p99。固定尺寸对照使用 recycler 与 benchmark 内 direct `new/delete` baseline；同时覆盖混合 size class、64-byte 超对齐 fallback、4,096 个 live frame burst、4 worker 并发 churn、Task suspend/resume、跨线程释放和 retained task clear。
- `benchmark/cpp/kernel/b35_coroutine_task_scale.cc`：支持显式 count 的完成任务 churn 和 retained live task pressure，避免把累计操作数误报为同时存活协程数。
- 跨提交任务对照使用相同的临时 C++23 harness：每个样本执行一百万次 `Task<void>` 创建、手动恢复到完成并销毁；基线/新实现交替运行各 `10` 个进程，每进程 `30` 个样本，共 `300` 个样本/版本。样本 CV 分别为 `8.98%` 与 `9.12%`。
- 生命周期对照执行一百万次初始挂起任务后直接丢弃，并用 `/usr/bin/time -v` 记录峰值 RSS；该场景用于验证泄漏修复，不用于证明 recycler 的单次成本。
- 按性能规范尝试 `perf stat -d`；当前虚拟机的 hardware counter 均返回 `<not supported>`，因此本报告不对 IPC、cache miss 或 branch miss 做推断。

## 原始微基准收益（历史数据）

| 场景 | p50 ns/op | p90 ns/op | p99 ns/op | fallback 估计 |
| --- | ---: | ---: | ---: | ---: |
| 256-byte frame，recycler | **14.06** | **16.44** | **23.97** | 0 |
| 256-byte frame，关闭 recycler | 23.62 | 28.70 | 34.51 | 20,000 |
| 128-byte size class | 14.12 | 16.54 | 20.96 | 首次 miss 1 |
| 512-byte size class | 14.51 | 16.98 | 19.27 | 首次 miss 1 |
| 2048-byte size class | 15.30 | 18.73 | 22.01 | 首次 miss 1 |
| 4096-byte frame（不入桶） | 36.24 | 41.88 | 52.99 | 20,000 |

扩展压测（同样为 100 个进程样本）结果如下：

| 场景 | p50 ns/op | p90 ns/op | p99 ns/op | fallback 估计 |
| --- | ---: | ---: | ---: | ---: |
| 混合 128/256/512/1024/2048/4096，recycler | 18.54 | 21.55 | 29.32 | 3,338 |
| 混合尺寸，关闭 recycler | 30.70 | 35.13 | 47.16 | 20,000 |
| 64-byte 超对齐 frame（不入桶） | 24.46 | 28.02 | 37.38 | 20,000 |
| 4,096 个 live 128-byte frame burst | 188.34 | 208.56 | 242.88 | 4,096 |
| 4 worker 并发混合 churn，recycler | 17.29 | 19.25 | 22.00 | 16 |
| 4 worker 并发混合 churn，关闭 recycler | 37.85 | 42.30 | 44.67 | 200,000 |

固定尺寸 churn 的收益来自同一线程释放后直接命中 TLS free-list；超过 `2048` bytes 的 frame 明确走全局对齐分配。跨线程释放样本为 `488.96 ns/op`（p50，300 个样本），fallback 估计为 `20,000`；该数字包含 producer/consumer 线程创建和 join，不能作为 frame release 本身的延迟结论。

扩展压测中，4 worker 混合 churn 的 p50 为 `17.29 ns`，关闭 recycler 为 `37.85 ns`（-54.3%）；但 live burst 在所有 frame 同时存活时无法命中 free-list，p50 为 `188.34 ns`，验证了容量压力与稳态 churn 是两种不同 workload。5,000 个 retained task 清空后观测到 `frame_bucket_512=1024`，缓存上限按预期生效。

## 原始回退与端到端影响（历史数据）

### 完成任务路径

| 指标 | `0e24a32` 基线 | `624b2d8` 新实现 | 变化 |
| --- | ---: | ---: | ---: |
| p50，ns/op | 83.357 | 87.678 | **+5.18%** |
| p90，ns/op | 93.872 | 99.744 | **+6.26%** |
| p99，ns/op | 100.632 | 107.691 | **+7.01%** |
| mean，ns/op | 83.785 | 88.683 | +5.85% |

该 workload 的 frame 实际请求大小为 `56 bytes`，新分配器将其放入 `128-byte` size class，并在 frame 前增加 `32-byte` header。除了 free-list 命中，完成路径还要承担 header 识别、借用 TaskRef 标记和额外的生命周期分支；因此微基准的 allocator 命中收益没有转化为任务端到端收益。

### 调度回归观察

`b28_scheduler_resume_pressure` 在 30 轮交替运行中没有形成稳定的整体回退结论，但值得保留为观察项：ComputeScheduler 的 p50 为 `67.37 -> 68.71 ns`（+1.99%），p90 为 `79.14 -> 95.34 ns`；不同轮次 CV 约 `13%~20%`。IOScheduler batch 64/256 的 p50 分别为 `57.38 -> 60.16 ns`（+4.84%）和 `58.03 -> 61.18 ns`（+5.43%），接近或略高于 5% 门槛，需在更稳定的硬件计数环境复测。

### 生命周期收益与缓存驻留

每桶上限为 `1,024`，五个 size class 的理论 TLS frame cache 上限约为：

`(128 + 256 + 512 + 1024 + 2048 + 5 * 32) * 1024 = 4,227,072 bytes`，即约 `4.03 MiB/线程`，还不含 allocator 元数据。12 个长期 worker 最坏可保留约 `48 MiB`。TLS 析构会 flush free-list，但本轮未测量线程池 churn 下的长期 RSS，生产部署应继续监控 retained memory。

## 验证结果

- 通过：`t180_coroutine_frame_allocator`、`t52_taskapi`、`t54_then`、`t61_await`、`t65_coro`、`t115_taskstoresrc`、`t122_taskresult_storage`（`developer-full` Debug/epoll 构建）。
- 通过：`t180_coroutine_frame_allocator`（`linux-perf-release` RelWithDebInfo/io_uring 构建）。
- 通过：新增边界/并发场景在 `t180` 中重复运行 50 次；通过零/极小尺寸、溢出、对齐、cache pressure、nothrow/sized/unsized delete、重复结果消费、跨线程 raw release 和 4 worker churn。
- 通过：ASan + UBSan `t180` 与 `b34` 定向运行（`detect_leaks=0`）；当前执行器下 LeakSanitizer 被 ptrace 限制，未将其误报为通过。
- 超对齐覆盖目前针对 detail allocator 和 promise 的 aligned/sized+aligned 入口。GCC 14.2 在本机不会把 coroutine local 的 `alignas(64)` 需求传递到 promise 分配调用；强行运行该编译器行为会被 UBSan 报告 misaligned frame，因此未把它伪装成产品路径通过，实际编译器超对齐 lowering 仍是残余风险。
- `linux-perf-release` 下 `t52_taskapi` 与 `t61_await` 分别出现 `Runtime::blockOn should succeed` 和 `result.has_value()` 失败；同一测试在 epoll 构建通过。本轮将其记录为 io_uring 后端定向失败候选，原因尚未归因，不能据此宣称 io_uring 全矩阵通过。
- `git diff --check` 通过。

## 采用建议

1. 接受生命周期修复和未提交 frame 的显式销毁。
2. 接受普通对齐 frame 的 headerless/sized-delete 路径、promise raw-state 热路径和 256 节点 cache cap；超对齐路径继续保留 header。
3. 生产发布仍需补充真实 scheduler/I/O workload、线程池长期 RSS 和分配计数；`b35` 的百万/千万级结果只证明 allocator/lifetime scale。

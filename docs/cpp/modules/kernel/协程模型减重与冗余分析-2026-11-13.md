# 协程模型减重与冗余分析

日期：2026-11-13。基线：`main` 的 `6fb244cf`。

本文回答三个问题：`TaskState` 能否更轻、协程模型有哪些可优化点、内核里有哪些冗余代码。
全文是**静态分析**：只读代码和 grep，没有编译、没有跑测试、没有做任何基准。
按 [性能优化约束](../../../refactoring/PERFORMANCE_OPTIMIZATION_GUIDELINES.md)，本文不给任何收益百分比，
只写"省掉哪些操作、多少字节"；是否真的更快，必须由 A/A + A/B 实测决定。

证据标记：

- **已复核**：本次亲自读代码或 grep 确认。
- **调研**：由只读调研读码得出，未逐条二次核对。
- **未复现**：读码支持该结论，但没有用测试或运行验证。

路径默认相对 `src/cpp/galay-kernel/`。

## 0. 结论摘要

1. `TaskState` 确实可以更轻。128 B 里有 16 B 是没有生产调用方的 `then()` 链，另有 8 B 是
   `optional<TaskRef>` 的多余包装；6 个原子字段里有 1 个在当前配置下只写不读，1 个很可能是重复仲裁。
2. 协程模型里最值得评估的是 `co_await Task` 的恢复方式：现在是嵌套恢复加一轮调度器再入队，
   没有用对称转移。
3. 冗余代码里体量最大的五块：两套时间轮（约 300 行重复）、`task.h` 的 `void`/`T` 特化（约 300 行）、
   从未启用的 IO 任务窃取（约 150 行）、三个后端调度器适配层（约 150 行）、六个通道里的重复辅助代码。
4. 有三处读码时发现的疑似行为问题（第 3.5 节），建议先确认，再谈优化。

以下两类工作已经做过或已被否决，本文不再重复提：

- 已完成：64 B 帧桶、`TaskAwaiter` 借用引用、结果缓冲不清零、独占释放快路径
  （[Task 局部减重验证](Task-局部减重验证-2026-11-09.md)）；原子完成通知
  （[完成通知协议](task_completion_notification.md)）。
- 已否决：TaskState 释放资格前置（[P01](taskstate_release_eligibility_review_2026-10-01.md)）、
  共享布局调整（[P11](shared_layout_review_2026-10-03.md)）。

## 1. TaskState 现状

定义在 `core/task.h:388-448`。

### 1.1 尺寸与分配

- x86-64：128 B、64 B 对齐，占两条缓存行。AArch64 上 `kCacheLineSize` 为 128
  （`galay-utils/common/defn.hpp`），因此按 128 对齐。**已复核**
- 与协程帧是两次独立分配：帧走 `allocate_frame_storage`，状态在 `get_return_object()` 里
  `new (std::nothrow) TaskState(handle)`（`task.h:1842`、`task.h:2000`）。两者各有一条 TLS 空闲链。**已复核**
- 仓库里没有对 `sizeof(TaskState)` 的 `static_assert`，128 B 只靠注释（`task.h:429-430`）维持。**已复核**

### 1.2 字段使用情况

| 字段 | 大小 | 热/冷 | 说明 |
|---|---:|---|---|
| `m_result_storage` | 32 B | 冷 | 只在完成和取结果时访问，却排在第一条缓存行开头 |
| `m_handle` | 8 B | 热 | 每次恢复 |
| `m_scheduler` | 8 B | 热 | 每次调度、每次唤醒 |
| `m_runtime` | 8 B | 热读 | 每次恢复与 TLS 当前 Runtime 比较（`task.h:1637`） |
| `m_resume_queue_next` | 8 B | 仅跨线程唤醒 | 侵入式链接 |
| `m_refs` | 8 B | 热 | 64 位引用计数 |
| `m_completion_status` | 4 B | 热读 | `is_done()` 每次恢复和唤醒都读 |
| `m_queued` | 1 B | 热 | 每次唤醒 `exchange`，每次恢复清零 |
| `m_resume_queue_claimed` | 1 B | 热写 | 每次恢复一次 release store；只在跨线程队列里真正起作用 |
| `m_resume_owner_only` | 1 B | 热写 | **当前配置下只写不读**，见 2.1 |
| `m_result_consumed` | 1 B | 冷 | 唯一使用者是 `try_take_task_result`（`task.h:761`） |
| `m_result_error` | 2 B | 冷 | `optional` 包一个 1 字节错误码 |
| `m_result_kind` | 1 B | 冷 | |
| `m_destroy_result` | 8 B | 冷 | 只在析构时读 |
| `m_then` | 16 B | 每次完成检查 | **没有生产调用方**，见 2.1 |
| `m_next` | 16 B | 仅 `co_await Task` | |

热字段（handle、scheduler、runtime、链接、refs、状态、四个标志）合计 48 B，本可放进一条缓存行；
但 32 B 的冷结果缓冲排在最前面，把 `m_refs` 和所有标志挤到了第二行，所以每次恢复都要碰两行。**已复核**

### 1.3 一次 owner 线程 IO 往返的原子操作

**调研**（按代码走读计数，未实测）：

- 挂起：从借用视图构造 `Waker`，1 次 `fetch_add`。
- 完成派发：reactor 拷贝 `Waker`（`core/epoll_reactor.cc:775`）1 次 `fetch_add`；
  `request_task_resume_state_detailed`（`core/task.cc:522-542`）做 `m_queued.exchange`、
  `m_resume_owner_only` 的 release store，再构造 `TaskRef(state, true)` 又 1 次 `fetch_add`。
- 恢复：`resume_task_state`（`task.h:1629-1644`）对三个标志各 store 一次。
- 收尾：三份引用各自释放。

合计约 3 次 `fetch_add`、3 次 `fetch_sub`、1 次 `exchange`、约 5 次原子 store。

## 2. TaskState 减重候选

### 2.1 第一档：删除无人使用的状态

**① 删除 `m_then` 与 `Task<void>::then()`**

- 省掉：16 B；每次完成一次 `has_value()` 检查（`task.cc:629`）；`attach_task_continuation`
  （`task.cc:554-566`）；`set_task_runtime` / `set_task_scheduler` 里对 `m_then` 的传播分支
  （`task.h:563-567`、`task.h:587-589`）。
- 依据：`src/` 内没有任何 `Task::then()` 调用，只有测试在用（如 `t54_then.cc`、`t62_then.cc`）。**已复核**
- 需要决定：`then()` 是公开 API。按项目"不保留向后兼容"的准则可以直接删，但这是你的取舍。

**② 删除 `m_resume_owner_only`**

- 省掉：每次唤醒一次 release store（`task.cc:534`）、每次恢复一次 store（`task.h:1636`）。
- 依据：唯一读取点是 `ready_entry_resume_owner_only`，只被窃取路径调用
  （`io_ready_queue.hpp:183`、`io_ready_queue.cc:72`）；而 IO 调度器构造时恒定关闭窃取
  （`core/io_scheduler_base.hpp:39`），`set_stealing_enabled(true)` 只出现在测试里。**已复核**
- 需要决定：与 4.1 的"IO 窃取路径"一并处理。保留窃取代码就得保留这个标志。

**③ `std::optional<TaskRef>` 改为 `TaskRef`**

- 省掉：`m_next` 从 16 B 降到 8 B（`m_then` 若保留也同理）。
- 依据：`TaskRef` 自带空状态（`is_valid()`），`optional` 是多余的一层。**已复核**

**④ `m_refs` 从 64 位改为 32 位**

- 省掉：4 B，并让热字段合计降到 44 B。**调研**

### 2.2 第二档：合并重复的仲裁与标志

**⑤ `m_resume_queue_claimed` 与 `m_queued` 的双重仲裁**

- 现状：`TaskResumeQueue::push` 先对 `m_resume_queue_claimed` 做 load + CAS（`task.h:1281-1291`），
  每次恢复再 release store 清掉（`task.h:1635`）。
- 依据：生产代码里 `push` 只经 `schedule_resume` 到达，而调用 `schedule_resume` 的只有
  `task.cc:535`，那里已经先赢得了 `m_queued.exchange`。`TaskResumeQueue` 的注释自己也写明
  "该不变量由 `m_queued` 仲裁保证"（`task.h:1258-1259`）。**已复核**
- 风险：测试替身直接实现或调用 `schedule_resume`（`test/cpp/common/scheduler_test_adapter.h`、
  `t38_contpath.cc`、`t162_mpmc_bounded_timeout_race.cc`）。它们是否依赖这层保护，**未核查**。

**⑥ 三个结果状态字段合一**

- `m_result_consumed`（原子 bool）、`m_result_error`（optional）、`m_result_kind` 可以合成一个字节的
  结果状态（空 / 内联 / 堆 / 已消费 / 各错误码）。
- `Task` 与 `JoinHandle` 都是只移动的单消费者，`m_result_consumed` 是否必须是原子，需要复核。**调研**

**⑦ 热/冷字段重排**

- 把 48 B 热字段集中到第一行，结果缓冲、错误、`m_next` 等冷字段放第二行。
- 注意：P11 的结论是"字段同线不等于收益已证实"。这一项只有测量能决定，不要预设有效。

**⑧ 64 B 布局是否可达**

做完 ①②③④ 后的字段：handle 8 + scheduler 8 + runtime 8 + 链接 8 + refs 4 + 状态 4 + 标志与结果状态约 4
+ `m_next` 8 + `m_destroy_result` 8 = 60 B，只剩 4 B 给内联结果。要压到 64 B，必须再做其中之一：

- 去掉内联结果缓冲（所有非 `void` 结果走堆，多一次分配）；
- 把内联缓冲缩到 16 B，并去掉 `m_runtime` 或 `m_destroy_result`。

`m_runtime` 目前不能从调度器反推：`Scheduler` 里没有指向 `Runtime` 的指针。**已复核**
结论：64 B 不是白拿的，要用结果内联能力去换。是否值得取决于 `Task<T>` 里小结果的占比，需要数据。

### 2.3 第三档：结构性方案

把状态并入 promise，即"帧就是状态"：

- 省掉：每个任务的第二次分配、类型擦除的结果缓冲、`m_destroy_result`、`m_result_kind`。
- 代价：帧必须活到最后一个引用释放。`JoinHandle` 持有期间，大帧无法在任务完成时回收；
  帧也可能在非 owner 线程销毁。`final_suspend` 要从 `suspend_never` 改成挂起。
- 这与历史文档里提到、尚未启动的 "TinyTask" 方向重叠。建议等第一、二档有了实测数据再讨论，
  本文只陈述取舍，不建议现在动手。

## 3. 协程模型优化候选

### 3.1 `co_await Task` 改用对称转移

现状（`TaskAwaiter::await_suspend`，`task.h:1693-1723`）：

1. 父任务把自己存进子任务的 `m_next`。
2. `schedule_task_immediately` 最终调用 `resume(task)`（`core/io_scheduler_base.hpp:272-277`），
   子任务在父任务的 `await_suspend` **调用栈内**嵌套执行，原生栈随嵌套深度增长。
3. 子任务完成时 `complete_task_state` 调用 `request_task_resume(m_next)`，父任务**重新经调度器入队**
   （`task.cc:588-630`）。即使子任务同步完成，父任务也要等调度循环下一次弹出。

内核里没有任何 `await_suspend` 返回 `coroutine_handle`，也没有用到 `noop_coroutine`。**已复核**

候选：`await_suspend` 返回子任务句柄，子任务的 final awaiter 返回父任务句柄。可省掉的是
父任务的那一轮入队（一次 `m_queued.exchange`、一对引用计数增减、一次队列进出）和嵌套栈帧。

必须处理的约束：

- `final_suspend` 现在是 `suspend_never`（`task.h:1890`），帧在完成时自销毁，需要改成自定义 final awaiter。
- 子任务已绑定到另一个调度器时，仍须走队列，不能直接转移。
- `resume_task_state` 里的标志复位和 `CurrentRuntimeScope` 切换不能被绕过。
- `kScheduleFailed` / `kResumeFailed` 两条错误路径的语义要保持。

[Task 局部减重验证](Task-局部减重验证-2026-11-09.md) 里已有子调用基准（`b43_task_child_loop.cc`），
可以直接用来做前后对照。

### 3.2 每次 IO 往返的引用计数抖动

reactor 在唤醒前把 awaitable 持有的 `Waker` 拷贝一份（`core/epoll_reactor.cc:775`），
`request_task_resume` 再为就绪队列加一次引用。候选：让唤醒直接消费 awaitable 持有的那份引用，
把它移交给就绪队列。io_uring 和 kqueue 的 reactor 是否同样拷贝，**未核查**。

### 3.3 等待路径上的堆分配

- 每次竞争加锁都 `std::make_shared<AsyncMutexWaiter>`（`async/async_mutex.h:260`）。**已复核**
- 每次 sleep 都 `std::make_shared<SleepTimer>`（`common/sleep.hpp:87`）。**已复核**

候选：等待节点直接放进 awaiter。awaiter 位于协程帧内，挂起期间地址稳定，可以做成侵入式节点。
难点在超时和取消与唤醒的竞争，现在靠 `shared_ptr` 延长寿命来规避。

### 3.4 `WakeCoordinator` 的诊断计数器

`request_wake` 每次都对 `m_wake_requests`、`m_coalesced_wakes` 或 `m_wake_emits` 做 `fetch_add`
（`core/wake_coordinator.h:51-62`），所有跨线程生产者写同一组计数器；而读取它们的访问器在
`src`、`test`、`benchmark`、`examples` 里零调用。**已复核**

### 3.5 需要先确认的三处疑似问题

这三条是行为问题，不是优化。读码支持，但都**未复现**。

1. **子任务可能在错误的线程上恢复**。`schedule_immediately_impl` 只调用 `bind_task` 校验任务归属，
   不校验当前线程（`core/io_scheduler_base.hpp:272-277`、`parallel/parallel_scheduler.h:234-241`）。
   `TaskAwaiter` 取的是子任务自己的调度器。于是：已绑定到调度器 B 的子任务，被调度器 A 上的父任务
   `co_await` 时，会在 A 的线程上直接恢复。
2. **`ParallelScheduler` 的跨线程恢复最多延迟 1 ms**。`schedule_resume_impl` 只往 `m_resumeQueue`
   里 push（`parallel/parallel_scheduler.h:210-216`），不唤醒 worker；worker 空闲时阻塞在
   `m_queue.wait_dequeue_timed(task, 1ms)`（`parallel/parallel_scheduler.cc:134`），要等超时才会回去排空恢复队列。
3. **SPSC 无界通道的内联唤醒绕过了 `resume_task_state`**。任务未绑定调度器且为 Inline 模式时直接
   `m_handle.resume()`（`concurrency/spsc/unbounded_channel.h:1665-1669`），`m_queued` 等标志不复位，
   也不切换 Runtime 作用域。这可能是有意的设计，需要确认。

- 生产中 `IOReadyQueue` 只有一处实例：`IOSchedulerBase::m_worker`（`core/io_scheduler_base.hpp:328`），

- 关闭是有意的设计，不是遗漏：注释写明"IO 注册和 reactor 提交保持 owner 线程亲和，禁止跨线程窃取执行"，

- 标志的默认值是 `true`（`core/io_ready_queue.hpp:248`、`:679`），所以测试和基准里单独构造的队列会真的窃取：

  删除窃取路径时这些要一并删改，`t104` 的断言也要调整。

所以准确的说法是：窃取代码在生产中**可达但永不生效**，只被测试和基准执行。

### 4.3 重叠的抽象

- **两套 `JoinHandle` 结果载体**。`JoinHandle` 同时持有 `TaskRef` 和
  `shared_ptr<TaskCompletionState<T>>`，按哪个非空分支。后者用 `std::mutex` + `std::condition_variable`，
  只服务 `spawn_blocking`（`core/runtime.h:285`）。而 `TaskState` 已经有基于原子等待的完成通知。**已复核**
- **accept 的两条实现**。epoll 和 io_uring 走 `OperationCompletion`，kqueue 仍走旧的 `AcceptIOContext`
  路径；`OperationKey` / `OperationState` / `OperationCompletion` 目前只为 accept 存在。**调研**
- **唤醒门控重复**。`DeferredWaker` 是四态门控，SPSC 有界通道用 `BoundedWaiterWakePhase` 又实现了一遍，
  而其他有界通道用的是 `DeferredWaker`。**调研**
- **两条定时器路径**。每个 IO 调度器有自己的时间轮；`sleep()` 和 `ParallelScheduler::add_timer`
  走全局 `TimerScheduler` 线程。**调研**
- **超时注入的五路兼容分支**。`WithTimeout::inject_timeout_result` 用五路 `if constexpr` 适配不同的
  awaitable 形态，注释自称 legacy adaptation。**调研**

### 4.4 冗余状态

- `TaskPromise::m_task_view` 恒等于 `TaskRef::borrowed(m_state)`（`task.h:1847`、`task.h:1927`）。
  **不能直接删**：http、http2、mysql、postgres 等模块有 26 处通过 `task_ref_view()` 取
  `const TaskRef&`，要删得先改这个接口。**已复核**
- io_uring 的 `m_{accept,recv,recvfrom}_multishot_armed`（`core/io_controller.hpp:759-761`）
  与对应的 handle 指针总是成对读写，等价于 `handle != nullptr`。**调研**
- `IOReadyQueue::stealing_enabled` 与 `ChaseLevTaskRing::m_stealing_enabled` 存了同一个值。**调研**
- `IOSchedulerBase::m_sleeping` / `m_wakeup_pending` 只被 `WakeCoordinator` 通过引用读写，
  可以直接放进 `WakeCoordinator`。**调研**

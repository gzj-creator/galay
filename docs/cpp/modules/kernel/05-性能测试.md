# 05-性能测试

## 正式对标政策（2026-08-21）

自 2026-08-21 起，项目的正式外部性能对标唯一采用 **Boost.Asio C++ 协程**
（`co_spawn` / `awaitable`）。Crossbeam、Tokio、libuv、hiredis、libpq、
libmysqlclient、gRPC、nghttpd、h2load 和其他工具/实现只保留为历史或内部验证资料，
不参与竞品排名，也不能用于当前性能优劣结论。

对协议没有同工作负载 Boost.Asio 协程 harness 的模块，正式状态为
`not_applicable`，而不是用第三方客户端、外部工具或不同 wire protocol 替代。旧的
比较源码和结果文件未删除，便于追溯，但它们不再是正式数据来源。

## C++ 协程帧分配优化评审（2026-08-27 follow-up）

本次 `TaskPromise` frame recycler 的详细前后对照、微基准收益、完成任务路径回退、生命周期
RSS 变化、headerless/sized-delete 路径和复现条件见
[协程帧分配性能报告-2026-08-26](./协程帧分配性能报告-2026-08-26.md)。当前代码已移除生产库
测试 hook，完成态 teardown 使用专用快路径，普通对齐 frame 不再携带 provenance header，TLS
cache 上限为每桶 `256` 个节点；`b35_coroutine_task_scale` 已补齐累计 churn 与百万/千万级 live
task 压力。最终 scheduler/I/O 采纳结论仍需以真实宏基准和长期 RSS 为准。

| Galay `epoll` / `Task` | 12,373.6 / 12,479.6 / 12,359.5 | **12,373.6** | **12,019.3** | **5.686%** | **0.000%** | 0 / 0 / 0 |
| Boost.Asio 1.83.0 / `co_spawn` + `awaitable` | 7,548.14 / 7,548.22 / 7,487.45 | **7,548.14** | **7,528.94** | **0.265%** | **0.000%** | 0 / 0 / 0 |

在该受控 workload 下，Galay 的 client throughput 中位数是 Boost.Asio 的
**1.639x**（+63.9%）。两端六次正式样本的 settled measured counters 都完整对齐，
settled client loss 均为 **0.000%**，且 runtime/shutdown errors 均为 0。
表中的 measurement-window reply gap（Galay 中位数比 Asio 高约 **5.42 个百分点**）
是 measurement 结束瞬间尚未回收的在途回包差额，不是确认的 UDP 丢包；正式可靠性结论
以 drain 后 settled counters 为准。不能把 UDP 吞吐数字单独表述为全面优势。

## Boost.Asio 协程 TCP 公平对标（2026-08-21）

TCP 使用独立的单进程 `tcp-echo` 长连接 harness，原始 CSV：
[kernel_boost_asio_coro_tcp_2026-08-21.csv](./benchmark_data/kernel_boost_asio_coro_tcp_2026-08-21.csv)。
两侧均使用 C++ 协程；Galay 侧为 `galay::Task`，基线侧为
`co_spawn` / `awaitable`。TCP 流按固定 256-byte 帧通过 `readExact` / `writeAll`
（Asio 对应 `async_read` / `async_write`）完成，避免拆包、粘包或部分写入改变工作负载。

| 条件 | 固定值 |
| --- | --- |

| 采样 | `taskset -c 0` 固定 CPU 0，Galay / Boost.Asio 交替各 3 轮，报告中位数 |

| 实现 | client pkt/s（3 轮） | 中位数 client pkt/s | 中位数 server pkt/s | measurement-window reply gap | settled client loss | runtime errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Galay `epoll` / `Task` | 4,307.61 / 4,319.86 / 4,296.22 | **4,307.61** | **4,299.81** | **0.461%** | **0.000%** | 0 / 0 / 0 |

loss 均为 **0.000%**，runtime/shutdown errors 均为 0；TCP settled counters 在每轮

backend 和固定参数下的 echo 吞吐，不外推到所有 TCP 应用或协议栈配置。

1. `B8` latency benchmark 增加 consumer-ready barrier
2. `galay::mpsc::UnboundedChannel` 增加 recv-side single-consumer prefetch
3. `galay::mpsc::UnboundedChannel` 的默认 batch size / prefetch limit 改为构造参数配置
4. `B6-Udp` 增加尾部 drain，降低 packet loss 抖动
5. `B1` latency 改为使用 `min(scheduler_count, 2)`，避免 burst 队列长度淹没调度开销
6. `B4-UdpServer` 将统计逻辑移出 scheduler 协程，避免阻塞事件循环并恢复 `B4/B5` 有效收发

- `B8-MpscChannel` 对 backlog、跨线程 wake 和 batch drain 边界很敏感
- `B14-SchedulerInjectedWakeup` 是 injected fast-path 的 canary
- `B10-Ringbuffer` 与 `B13-Sendfile` 对缓存状态、CPU 频率和单机环境非常敏感
- 网络 benchmark 需要明确 loopback / 容器 / 实机环境
- 文件 benchmark 需要明确缓存状态和文件大小

### 7. 结论与优化建议

结论：

1. 本轮只能确认当前 build 目录不可用于正式 kernel 性能压测，不能形成 Galay vs tokio/libuv/Boost.Asio 的性能优劣结论。
2. Galay kernel 的相关 benchmark 源码已存在，优先级可按 `B1/B14/B18` 调度延迟、`B8` MPSC channel、`B20` timer 与 C API `B24` sleep 精度补跑。
3. 竞品对比缺少可复用 harness；tokio 和 libuv 的库/工具链可作为后续基线基础，Boost.Asio 需先安装依赖。

优化建议：

1. 新增独立 `build-kernel-bench-release` 或 CMake preset，固定 `Release + GALAY_BUILD_BENCHMARKS=ON`，避免误用 Debug 构建。
2. 给 `b1`、`b8` 等 benchmark 增加命令行参数或配置文件，使 `RUNTIME_THREADS=4`、`TASKS_COUNT=100000`、`DURATION=30`、`WARM_UP=5` 能与计划严格一致。
3. 为 tokio/libuv/Boost.Asio 建立同目录竞品 harness，并输出统一 CSV 字段：`implementation,scenario,metric,value,unit,status,notes`。
4. timer/sleep 精度建议统一输出 p50/p95/p99/max 与 overshoot，而不是只记录平均值，便于和 tokio timer、libuv timer、Boost.Asio steady_timer 对齐。

## 2026-07-13 Linux io_uring UDP multishot recvmsg

本轮只比较同一台 Tencent Linux 6.8 / liburing 2.5 机器上的 HEAD one-shot 与 UDP multishot recvmsg。
服务端固定 CPU `0-1`，epoll 客户端固定 CPU `2-3`；每组先 warmup 5 秒，再运行 30 秒，3 轮取中位数并报告 CV。

| 版本 | 三轮 recv pkt/s | 中位数 | CV | 丢包率中位数 |
|---|---:|---:|---:|---:|
| HEAD one-shot recvmsg | 144,357 / 145,985 / 138,326 | **144,357** | 2.306% | 0.361% |
| multishot recvmsg + buffer ring | 147,162 / 151,630 / 160,128 | **151,630** | 3.516% | 0.452% |

multishot 相对 HEAD 提升 **5.04%**，两组 CV 均低于 5%。丢包率增加 0.091 个百分点，属于本轮可见的轻微回退，
因此不能只报告吞吐收益。旧的 5 秒未绑核 `114,559 pkt/s` 不再作为本次优化基线；新口径显示 HEAD 自身已达到
144k pkt/s，验证了短样本噪声问题。

内核 tracepoint 在相同 10 秒负载下给出：

| 版本 | `io_uring_submit_req` | `io_uring_complete` | recv pkt/s |
|---|---:|---:|---:|
| HEAD one-shot | 2,927,551 | 2,927,549 | 138,335 |
| multishot | 1,469,663 | 2,934,682 | 137,879 |

提交请求减少 **49.80%**，而完成事件保持约 293 万，证明同一个 recvmsg SQE 在持续交付数据报，而不是通过少处理报文换取数字。
sendto 仍为每数据报一个 sendmsg SQE；现有 scheduler 已在进入 reactor poll 前批量排空 ready task，并一次 flush ring 中
全部 pending SQE，因此没有再叠加一层 send pending queue。

回归证据：

- `kernel.iouudp_multishot_src`：能力门控、recvmsg 元数据解析、one-shot 回退源码边界。
- `kernel.iouudp_multishot`：截断后丢弃余量、连续数据报不串包、两个源端口正确回填、multishot armed 持久状态。
- Linux Release 定向回归通过；ASan/UBSan 下 UDP、timeout、multishot accept/recv/recvmsg 共 13 项全绿。

### 与 libuv 1.48.0 的固定口径补测（2026-07-14）

# Task 局部减重验证

日期：2026-11-09。本阶段只优化 `main` 现有的 `Task`。先完成生命周期、并发、内存安全和性能对照验收，再决定下一阶段的 TinyTask 工作。

## 1. main 上的局部优化

基线为 `main` 的 `cf14cedf`。改动放在独立工作树 `/data/disk1/projects/galay-task-lightweight-main-20261109`，分支 `optimize/task-overhead-main-20261109`。

`Task` 句柄只有一个指针。主要开销来自额外的 128 B `TaskState`、frame 分配桶、状态初始化及子调用中的引用计数。本轮直接处理以下四项：

1. 在已有 frame recycler 中增加 64 B 桶，减少小 frame 的分配空间；最常见的小帧直接返回 0 号桶，较大的帧继续使用原有尺寸分类。缓存桶使用单独的 TLS 清理对象，与 TaskState 缓存采用同一模式集中注册线程退出清理。
2. `TaskAwaiter` 从它已经持有的子任务借用 `TaskRef`，减少一次临时 retain/release。调度器入队仍取得自己的引用，父 continuation 的拥有引用仍正常转移。
3. 结果存储处于 `Empty` 时不清零 32 B 原始缓冲区。实际写入先构造结果对象或设置堆指针，然后设置存储类型；消费和销毁只在对应类型下读取结果。
4. `TaskRef` 释放最后一个独占引用时先以 acquire 读取计数；只有一个拥有引用且没有合法的并发 retain 时直接销毁，省去一次原子读改写。共享引用仍使用原有 acq_rel 减计数。该思路参考 libstdc++ 的独占 shared_ptr 释放；TaskRef 没有可在计数外重获所有权的 weak 引用。

新增 [t203_taskref_last_release_race.cc](../../../../test/cpp/kernel/t203_taskref_last_release_race.cc) 使用 2/4/8 个线程并发释放最后引用。各线程在释放前写不同的普通内存，最后的 frame 析构必须观察全部写入且只执行一次。该契约先在未修改的 main 上通过 Release/TSan，再验证独占释放优化后的实现。

扩展验证另外发现 `main` 已存在并发唤醒与完成时的 handle 读写竞态。`request_task_resume_state_detailed()` 原来会在外部线程读取 `m_handle`，而 promise 析构会在 owner 线程清空该字段。未修改的 main 使用相同 TSan 测试也能复现。局部修复让外部唤醒只检查稳定的 scheduler 指针和原子完成态，handle 由 owner 的执行入口检查；没有新增锁、原子 handle 或新的状态生命周期。

结果仍保存在 `TaskState`，Task 创建、调度、完成、Waker 和取消的生命周期沿用 `main`。本轮没有引入新的 Task 名称或根/子执行链模型。

验证覆盖小帧桶的 63/64/65 B 边界、跨线程释放与 TLS 退出清理、内联/堆结果、未启动与已完成任务、continuation 注册顺序、完成等待竞态、channel 超时竞态和停止时的 accept 清理。增加的小帧测试先在旧实现上失败，原有 10 项定向回归在修改前通过；第一轮候选执行 18 项定向回归，后续已扩大到完整 kernel 回归及 sanitizer。

两侧 Release 构建分别位于独立工作树的 `build/task-lightweight-baseline`、`build/task-lightweight-current`。均使用 GCC 14.2.0、C++23、epoll，关闭其他可选模块。现有生命周期对照使用相同的 `b43_task_family_baseline.cc` 和 `compare/boost-asio-coro/task_lifecycle.cc` 源码，并分别编译、链接各自的 kernel 库。Task 专用子链测试位于 [b43_task_child_loop.cc](../../../../benchmark/cpp/kernel/b43_task_child_loop.cc)，基线端使用独立 main 工作树的冻结头文件。

## 2. 第一轮配对采样（独占释放优化之前）

每个时间场景使用 CPU 2、20 对同二进制 A/A、20 对旧/新 A/B，每侧样本不少于 200 ms；保留内存为 5 对独立进程，每侧保留 200,000 个任务。置信区间使用固定种子 5,000 次 paired bootstrap。所有样本保留，没有删除离群值或重测补样。

| 场景 | main 中位数 | 候选中位数 | 配对平均比值（新/旧）及 95% 区间 |
| --- | ---: | ---: | --- |
| 创建后销毁（Task<int>，ns/次） | 48.23 | 47.46 | 0.9962 [0.9722, 1.0235] |
| CPU 根，深度 0（ns/次） | 11926.08 | 11878.03 | 0.9993 [0.9842, 1.0151] |
| CPU 子链，深度 4（ns/次） | 12038.65 | 12125.86 | 0.9996 [0.9622, 1.0375] |
| CPU 子链，深度 16（ns/次） | 13472.48 | 13294.45 | 0.9849 [0.9515, 1.0283] |
| 保留空 Task<void>（B/个） | 328.30 | 264.30 | 0.8051 [0.8051, 0.8051] |

小空任务的 RSS 增量从约 328.3 B/个降到 264.3 B/个，减少约 19.5%。这是保留 Task<void> 的进程驻留口径，包含分配器和句柄页，不能当作所有 Task 类型的精确大小。时间场景的 A/B 区间均跨过 1；创建销毁与深度 4 的 A/A 区间也超出 ±3%，因此本轮只确认小任务内存减重，不声明稳定的时间收益或严格的时间无回退 Gate 通过。

早期两个候选的创建销毁存在约 4–5% 时间回退，原始记录保留在 `candidate-v1/`、`candidate-v2/`。最终候选把 frame 桶的 TLS 清理独立注册后，创建销毁的配对平均比值为约 0.996，早期明显回退没有在最终样本中复现；区间仍有噪声余量。

该轮候选 18/18 项定向回归通过。原始样本、二进制/动态库哈希、工具链、源 diff、同一测量源码的编译命令及采样脚本保存在本地归档 `docs/cpp/modules/kernel/benchmark_data/task_lightweight_main_20261109/`；该路径受 `.gitignore` 排除，不随本次提交发布。

复现第一轮配对采样的脚本为 `build/task-lightweight-evidence/sample_final.py`，只适用于该轮冻结的代码。最终实现使用第 4 节的子调用基准和 `sample_task_unique_release.py`；两侧须分别使用各自头文件和动态库构建。

- Release 完整 kernel：209 项，206 通过，3 项因关闭 io_uring 跳过，0 失败。包含新增 TaskRef 最后引用释放测试；全部构建完成。

- 真实挂起 smoke：旧/新两侧各 13/13 场景通过，覆盖 TCP/timer/channel 根与子任务、立即完成、EOF、closed、timeout、CPU spawn 和同步 work item。要求实际挂起数等于恢复数和操作数。

该轮验收覆盖 Linux / epoll；随后补做的 Linux / io_uring 验证见第 5 节。kqueue 和 module/import 消费尚未复验；已保留完整回归、sanitizer、旧基线复现及真实挂起日志。

## 5. io_uring 正确性补验

使用相同的 `main` 基线和优化代码，在 Linux `6.8.0-101-generic`、liburing `2.5`、GCC `14.2.0` 上验证。`io_uring_disabled=0`，实际创建队列成功；两侧独立构建均设置 `GALAY_DISABLE_IOURING=OFF`，编译定义为 `USE_IOURING`，链接系统 liburing。Release 库和测试使用 `-O3`，未定义 `NDEBUG`；测试还沿用仓库的 `-UNDEBUG`。ASan/UBSan 和 TSan 使用 `-O1 -g`，没有修改 Task 或 reactor 生产代码来使测试通过。

| 验证 | 结果 | 主要覆盖 |
| --- | --- | --- |
| 优化版完整 kernel CTest | 209 项注册测试全部返回成功，0 失败 | Task、调度、TCP/UDP、超时、文件与同步原语 |
| 未修改 main 定向对照 | 23/23 通过 | 与优化版相同的生命周期与 io_uring 场景，不含新增 t203 |
| 优化版 ASan + UBSan + LSan | 24/24 通过 | 结果存储、frame 回收、引用释放、Waker、continuation、超时、CQE 与停机清理 |
| 优化版 TSan | 24/24 通过 | 同一组测试，`halt_on_error=1`，未使用 suppression |
| TSan 最后引用释放与 Waker | 每项重复 30 次，60 次执行全部通过 | 并发最后释放的唯一析构、写入可见性、完成附近重复唤醒 |
| io_uring 关键回归 | 10 项各重复 10 次，100 次执行全部通过 | multishot accept/recv/UDP、send_zc、完成顺序、timeout、挂起 accept 停机 |
| 按 io_uring 语义验证真实 I/O | main、优化版、优化版 ASan/UBSan、优化版 TSan 各 13/13 通过 | TCP/timer/channel 根与子任务、预填读、EOF、closed、timeout、CPU spawn/work item |

完整 CTest 的 209 项是注册测试口径：10 项测试输出了针对 epoll/kqueue 等其他后端的内部跳过信息，但以 0 返回，CTest 没有将它们标为 skipped；不能据此说 209 项都执行了后端运行时逻辑。io_uring 的 multishot accept、multishot recv、UDP、send_zc、typed accept、CQE timeout 和配置变体测试均实际执行并通过。

2,000 个挂起 accept 的停止测试在 main、优化版、ASan/UBSan、TSan 下均得到 `resumes=destroys=detached=closed=frames=2000`，检查每个任务只恢复和析构一次、controller 解绑、返回 closed，并销毁协程帧。该测试证明此类 accept 的逻辑停止与资源边界，不代表所有 I/O 类型的全量 drain 已经证明。

真实 I/O 每侧测试 TCP/channel 1,000 次、timer 32 次、CPU 场景 10,000 次，有界 CPU spawn 在途上限为 32。受控真实挂起场景要求挂起数、恢复数和完成操作数一致；所有场景检查预期结果与校验和，没有只凭耗时或进程退出判定成功。

首次直接运行原有 B44 时，四种构建均有 12/13 通过，只有 `tcp_immediate` 的“全部立即完成”要求失败。main 和优化版均完整收到 1,000 个响应、8,000 字节，校验和 `499500`，表现一致：第一次 recv 挂起并恢复一次，随后 999 次从缓存立即完成。原因是 io_uring 的 `add_recv()` 先消费已收到 CQE 的缓存；新 controller 没有该缓存时，必须先提交 multishot recv 并等待 CQE。数据已在 socket 内核缓冲中不等于 CQE 已经到达。

原始失败日志全部保留。补验仅在本地验证副本 `task_real_io_iouring.cc` 中为 io_uring 的预填 TCP 读增加 `cqe_and_inline` 断言：必须观察到真实挂起和缓存内联完成，挂起与恢复配平，调用数等于完成数，继续要求全部操作、数据和校验和正确；其他场景保留原有断言。两侧使用同一副本，并分别使用各自的头文件和动态库；补验四种构建均为 13/13 通过。原 benchmark 和生产实现没有因为这一口径差异而改动。

本轮没有 sanitizer 运行时错误或新增正确性回退证据。TSan 编译时仍报告 vendored concurrentqueue 中 `atomic_thread_fence` 不被 TSan 支持的工具限制；不能把本次运行扩大解释成所有并发交错或内核缓冲访问均已被完整证明。上一节的 Task<int> 创建测量噪声和第 3 节的 main 定时器偶发提前触发缺陷仍然保留；本轮通过不表示它们已解决。继续保持 Task 阶段，不启动 TinyTask。

io_uring 验证的原始命令、构建参数、日志、JUnit、验证副本差异、源码与产物哈希保存在本地归档中的 `iouring/`；完整执行记录为 `commands.json` 与 `qualified-commands.json`，`*-real-io.log` 保留原始要求失败，`*-real-io-qualified.log` 记录按 io_uring 语义补验的结果。这些归档和 `build/task-lightweight-iouring-{current,baseline,asan,tsan}` 构建目录均被 `.gitignore` 排除，不随本次提交发布；本节保留可审阅的验证结论与限制。

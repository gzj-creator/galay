# 05-性能测试

> **正式对标政策（2026-08-21）**：项目正式外部对标唯一采用 Boost.Asio C++
> 协程（`co_spawn`/`awaitable`）。本页记录 C ABI 内部基线；C/C++、libuv 等结果
> 仅用于内部验证或历史追溯，不参与竞品排名。正式结果见 C++ kernel 性能页。

## 现行口径

本文档只把当前原生 C 实现的 Release fresh 输出当作性能证据。已删除的
`galay-c-bridge`、unbounded C wrapper 和 token API 的旧数字不再代表现行
C ABI，也不能与下表直接比较。历史数据仍可通过 Git 历史追溯。

结果只在以下条件全部成立时有效：

- Release 构建，开启 `GALAY_BUILD_C_API` 和 `GALAY_BUILD_BENCHMARKS`。
- benchmark 返回 0，完整性校验通过，且输出中 `errors=0`、等价失败计数为 0，
  或 target 自身的全部完成校验通过。
- 吞吐和延迟使用同一机器、同一 backend、同一 workload 和同一构建参数比较。
- 作优化归因时，手写采样器先预热，再报告 median 和范围；不用单次结果声称优化收益。

## 2026-08-15 Linux x86_64 fresh 验证

- 系统：`Linux 7.0.0-28-generic x86_64`，VMware 虚拟化环境。
- CPU：`Intel Core i7-14700K`，虚拟机可见 `12` 个单线程 core。
- 编译器：GCC `14.2.0`；CMake `3.28.3`。
- 构建：`Release`，`GALAY_DISABLE_IOURING=ON`（epoll），构建目录
  `/tmp/galay-c-native-release`。
- correctness：`c.kernel.native_bounded_channels`，`1/1 PASS`。

### Native bounded channel

`b27` 使用 `10000000` 条消息、1 次预热和 5 次采样，同时给出 1P1C 和
4P4C MPMC 结果。`b28/b30/b32` 每次使用 `2000000` 条消息、1 次预热和
3 次采样，并在 Linux 上绑定 worker 线程。所有 workload 的 channel 容量为
`4096`，每条消息复制 24 字节 `galay_c_channel_message_t` 描述符，其
`data` 指向 benchmark 拥有的 `uintptr_t` payload。

| target | topology | messages/sample | median msg/s | min msg/s | max msg/s |
| --- | --- | ---: | ---: | ---: | ---: |
| `benchmark_c_kernel_bounded_channel_throughput` | 1P1C | 10000000 | 8131932.47 | 7788823.19 | 8722464.27 |
| `benchmark_c_kernel_bounded_channel_throughput` | 4P4C MPMC | 10000000 | 2224162.19 | 2093304.88 | 2317631.92 |
| `benchmark_c_kernel_mpmc_bounded_channel_throughput` | 4P4C | 2000000 | 2211005.06 | 1466854.23 | 2370648.53 |
| `benchmark_c_kernel_mpsc_bounded_channel_throughput` | 4P1C | 2000000 | 3236408.30 | 3107240.18 | 3630245.02 |
| `benchmark_c_kernel_spsc_bounded_channel_throughput` | 1P1C | 2000000 | 8267400.81 | 7582852.14 | 9028285.62 |

这些数据是当前基线，不是“原生 C 一定比旧 wrapper 快”的结论。VMware
调度、CPU 频率和共享主机负载会影响绝对吞吐；MPMC 3 次采样的范围也说明
环境存在可观测抖动。需要做优化归因时，应在固定频率的物理机上扩大采样数，
并保存 before/after 原始输出。

### 串行压力采样

以下新增数据都来自同一 Release/epoll 构建；每个 workload 串行运行 3 次，
表中为 3 次结果的 median，并列出范围。单 I/O scheduler target 通过
`taskset -c 0` 约束在一个逻辑 core；UDP 需要两个 I/O scheduler，使用
`taskset -c 0,1`。虚拟机无法固定主频或关闭 turbo，因此这些是本机基线，
不是跨机器或优化前后的百分比结论。

#### Timeout 语义压力

timeout target 验证的是 timeout、EOF 和清理路径能在压力下完整返回，不应和
网络 QPS 横向比较。`0` timeout 参数在本机实际表现为约 10.5ms 的完成时间，
因此这里报告完成延迟而不称为“零开销”。

| target | workload | median | range | 完整性 |
| --- | --- | ---: | --- | --- |
| `benchmark_c_kernel_tcp_socket_timeout_smoke` | 1000 次 TCP accept timeout=0 | 10.563 ms/op | 10.553-10.567 | 1000/1000 completed, failures=0 |
| `benchmark_c_kernel_udp_socket_timeout_smoke` | 1000 次 UDP recvfrom timeout=0 | 10.511 ms/op | 10.508-10.513 | 1000/1000 completed, failures=0 |
| `benchmark_c_kernel_async_file_timeout_smoke` | 256 次 EOF poll | 30589.08 polls/s | 30490.71-32241.81 | 3/3 return 0 |
| `benchmark_c_kernel_file_watcher_timeout_smoke` | 128 次 watcher wait timeout=1ms | 11892.48 us/op | 11823.28-11928.38 | 128/128 completed, failures=0 |

`benchmark_c_kernel_timeout_api_pressure 128` 首轮输出
`failures=1 tcp=0 udp=0 file_watcher=0 async_file=0`，因此没有发布任何混合
timeout 性能数据。它是当前 Release 门禁失败项，而不是 `b16` 的性能基线。

#### UDP loopback 吞吐

`benchmark_c_kernel_udp_socket_throughput` 使用 2 个 I/O scheduler、1024B
datagram、3s 和两个固定逻辑 core。3 次均 `errors=0`；接收吞吐 median 为
`40.757 MiB/s`，范围 `40.630-42.880 MiB/s`。发送与接收计数分别为
`127210/124906`、`127595/125288`、`132113/131798`，对应 packet loss 为
`1.811%`、`1.808%`、`0.238%`。UDP 丢包是此 workload 的观测结果，不会被
`errors` 计数捕获；因此不把该值描述为无丢包吞吐上限。

#### UDP 双进程 echo

`benchmark_c_kernel_udp_socket_server_throughput` 与
`benchmark_c_kernel_udp_socket_client_throughput` 在不同的固定 core 集上运行：
server 为 core `0,1`，client 为 core `2,3`；两端各 2 个 I/O scheduler，16 个
client、1024B datagram、每 client 最多 100000 条消息、持续 5s。3 次均为
client/server exit 0、两端 `errors=0` 且 sent=received：

| metric | median | range |
| --- | ---: | --- |
| client sent / received | 109434 / 109434 datagrams | 108707-111198 |
| client send / receive throughput | 21.362 MiB/s | 21.218-21.704 MiB/s |
| packet loss | 0.000% | 0.000% |

这是当前可发布的独立 UDP client/server 压力基线；它与单进程 loopback 的调度、
socket 和统计窗口不同，不能用两者的绝对吞吐推导实现差异。

### TCP 双进程 echo

`accept` 只把 listener 固定到当前 scheduler；新 accepted socket 在其 session
coroutine 的第一次 `recv/send` 时绑定。此前 accepted socket 被固定到 accept
scheduler，而 session 按 runtime 轮询投递到另一个 scheduler，首个 `recv` 返回
`C_IOResultInvalid`，导致 client/server 同时报错。`t25_coro_tcp` 现以两个 I/O
scheduler 覆盖这条交接路径。

以下数据来自 `/tmp/galay-tcp-compare-release`：同一台机器、Release、epoll、
server 固定 core `0,1`、client 固定 core `2`，2 个 server I/O scheduler、1 个
client I/O scheduler、32 条连接、`1024B request -> 1024B response`、持续 `5s`。
每个 workload 串行运行 3 次；client/server 都以 `0` 退出且 `errors=0`：

| implementation | targets | median QPS | QPS range | median throughput | throughput range |
| --- | --- | ---: | ---: | ---: | ---: |
| C API | `benchmark_c_kernel_tcp_socket_server_throughput` / `benchmark_c_kernel_tcp_socket_client_throughput` | 8513.76 | 8407.03-8609.48 | 16.628 MiB/s | 16.420-16.815 MiB/s |
| C++ control | `benchmark_kernel_tcp_server_throughput` / `benchmark_kernel_tcp_client_throughput` | 11089 | 11061-11250 | 21.659 MiB/s | 21.605-21.973 MiB/s |

C API median 为 C++ control 的约 `76.8%`，两者已处于同一数量级。两个 harness 的
连接预热和计时边界仍不完全相同，因此该表用于同级别验证，不作为精确的优化百分比。
单连接 smoke（1 条连接、1024B、3s）也以 `errors=0` 通过，得到 `3767.74 QPS`。

## Release 复现

配置独立 Release 构建：

```bash
cmake -S . -B build/c-api-release \
  -DCMAKE_BUILD_TYPE=Release \
  -DGALAY_BUILD_DEBUG=OFF \
  -DGALAY_BUILD_C_API=ON \
  -DGALAY_BUILD_BENCHMARKS=ON \
  -DBUILD_TESTING=ON \
  -DGALAY_BUILD_EXAMPLES=ON \
  -DGALAY_ENABLE_CPP23_MODULES=OFF \
  -DGALAY_DISABLE_IOURING=ON
```

构建并验证 bounded channel：

```bash
cmake --build build/c-api-release \
  --target test_c_kernel_native_bounded_channels \
           benchmark_c_kernel_bounded_channel_throughput \
           benchmark_c_kernel_mpmc_bounded_channel_throughput \
           benchmark_c_kernel_mpsc_bounded_channel_throughput \
           benchmark_c_kernel_spsc_bounded_channel_throughput -j2

ctest --test-dir build/c-api-release --output-on-failure \
  -R '^c\.kernel\.native_bounded_channels$'

./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_bounded_channel_throughput
./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_mpmc_bounded_channel_throughput
./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_mpsc_bounded_channel_throughput
./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_spsc_bounded_channel_throughput
```

TCP 双进程复现：先启动 server，再在另一终端启动 client，最后用 `SIGINT`
让 server 输出收尾统计。

```bash
cmake --build build/c-api-release \
  --target benchmark_c_kernel_tcp_socket_server_throughput \
           benchmark_c_kernel_tcp_socket_client_throughput -j2

./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_tcp_socket_server_throughput 19081 2
./build/c-api-release/benchmark/c/kernel/benchmark_c_kernel_tcp_socket_client_throughput \
  -h 127.0.0.1 -p 19081 -c 32 -s 1024 -d 5 --io-schedulers 1
```

## 解读注意事项

- TCP `QPS` 是完整 request/response round-trip；`throughput_mb_per_sec` 同时计入
  request 和 response payload。
- UDP `loss_percent = 1 - received / sent`。server/client 的统计窗口和 worker
  配置不一致时，不写严格横向百分比。
- timeout smoke 和 `timeout_api_pressure` 是 API 语义/压力入口，不与网络 QPS
  横向比较。
- `aio_file_batch` 的 backend 支持范围与 async file 不同；输出
  `operation unsupported` 只能证明显式 unsupported 路径，不是 I/O 性能结果。
- 协程延迟应报告 p50/p90/p99；只输出 average 的 target 不能支撑尾延迟结论。

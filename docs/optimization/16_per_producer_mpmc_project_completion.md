## 技术亮点

### 1. 创新架构设计

**Per-Producer Ring 模式**:
```
Producer 1 → Ring 1 ──┐
Producer 2 → Ring 2 ──┼──→ Consumer 轮询
Producer 3 → Ring 3 ──┘
```

**核心优势**:
- ✅ 零 producer 竞争
- ✅ 缓存友好
- ✅ 易扩展

### 2. 性能优化技术

#### 无竞争写入
```cpp
// Producer 写入无需 CAS
m_tail.store(tail + 1, std::memory_order_relaxed);
```

#### 批量读取
```cpp
// 一次读取多条消息
size_t tryRecvBatch(T* output, size_t maxCount);
```

#### 缓存行对齐
```cpp
alignas(kCacheLineSize) std::atomic<uint64_t> m_tail{0};
alignas(kCacheLineSize) std::atomic<uint64_t> m_head{0};
```

## 问题解决过程

### 遇到的主要问题

#### 问题 1: 高负载下消息遗漏 ❌ → ✅

**现象**: 4P1C 4000 消息卡在 1500-3000 条

**根本原因**: 
- `tryRecvBatch` 的 CAS 逻辑在单 consumer 场景下有问题
- 轮询策略使用 `fetch_add` 导致索引跳跃

**解决方案**:
1. 简化 `tryRecvBatch`，移除 CAS，直接更新 head
2. 简化轮询策略，每次从头开始扫描

**结果**: ✅ 所有测试通过

#### 问题 2: 多 consumer 竞争 ❌ → ✅

**现象**: testMultipleConsumers 超时

**根本原因**: 单 consumer 优化与多 consumer 测试冲突

**解决方案**: 在 channel 层面添加 mutex 保护

**结果**: ✅ 所有测试通过

### 关键决策

#### 决策 1: 单 consumer 优化 vs 多 consumer 并发

**选择**: 单 consumer 优化 + channel 层 mutex

**理由**:
- 大多数场景是 1-4 个 consumer
- Ring 层面无 CAS 更快
- Channel 层 mutex 简单可靠

**结果**: ✅ 性能优异，实现简单

#### 决策 2: 轮询策略

**选择**: 简单的全扫描策略

**理由**:
- 确保不遗漏消息（正确性优先）
- 实现简单，易于验证
- 性能足够好

**结果**: ✅ 稳定可靠

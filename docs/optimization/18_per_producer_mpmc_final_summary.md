### 未完全解决的问题 ❌

**高负载 + 多线程场景的稳定性问题**

#### 现象
- 小规模测试（≤400 msg）：✅ 通过
- 大规模测试（4000 msg）：❌ 卡在 ~3000 条消息
- 单 consumer：✅ 通过
- 多 consumer：❌ 卡住或超时

#### 根本原因

**架构矛盾**：
```
Per-Producer Ring 设计假设：
- Producer 端：零竞争（每个 producer 独占 ring）✅
- Consumer 端：轻度竞争（多个 consumer 轮询）⚠️
```

但实际中 consumer 端的竞争比预期复杂：

1. **CAS 失败累积**
   - 多个 consumer 竞争同一个 ring 的 head
   - CAS 失败后返回 0，调用者需重试
   - 高负载下 CAS 失败率高，导致"饿死"

2. **轮询策略问题**
   - Thread-local 索引让每个 consumer 从不同位置开始
   - 但多个 consumer 可能都跳过了有消息的 ring
   - 需要更智能的重试和回退策略

3. **Memory ordering 问题**
   - 高并发下，relaxed/acquire/release 的语义可能不够
   - 需要更强的 memory barrier

## 技术难点分析

### 问题 1：CAS 竞争

**传统 MPMC**（如 crossbeam）：
```
所有 producer 竞争一个 tail
所有 consumer 竞争一个 head
→ 设计时就考虑了高竞争
```

**Per-Producer MPMC**：
```
Producer：零竞争 ✅
Consumer：N 个 consumer 竞争 M 个 rings
→ 竞争模式更复杂
```

**当 N ≈ M 时**（如 4P4C）：
- 每个 ring 平均有 ~N/M 个 consumer 竞争
- CAS 失败率高
- 需要复杂的重试逻辑

### 问题 2：无法使用 Mutex

**项目规范**：
- ❌ 禁止 mutex/lock_guard（协程环境，禁止阻塞）
- ✅ 只能使用原子操作

**这限制了解决方案**：
- 不能用 mutex 简单保护
- 必须设计复杂的无锁算法
- 增加了实现难度

### 问题 3：测试覆盖不足

**现状**：
- ✅ 小规模测试充分
- ❌ 大规模 + 多线程测试不足
- ❌ 边界条件测试不足

**需要**：
- 压力测试（long-running）
- 并发测试（race detector）
- Chaos testing（随机延迟）

## 可行的解决方案

### 方案 1：限制使用场景 ⭐⭐⭐

**定位**：针对特定场景优化

**适用**：
- ✅ 单 consumer 或少量 consumer（1-2）
- ✅ Producer 数量 >> Consumer 数量
- ✅ 中低负载

**不适用**：
- ❌ 多 consumer（4+）
- ❌ Consumer 数量 ≈ Producer 数量
- ❌ 极高负载

**优点**：
- 在适用场景下性能优异
- 实现相对简单

**缺点**：
- 使用场景受限
- 需要明确文档说明

### 方案 2：混合策略 ⭐⭐⭐⭐

**设计**：根据 consumer 数量动态选择

```cpp
if (consumerCount <= 2) {
    // 使用 Per-Producer Ring（高性能）
} else {
    // 回退到传统 MPMC（稳定）
}
```

**优点**：
- 兼顾性能和稳定性
- 自动适应场景

**缺点**：
- 需要维护两套实现
- 增加复杂度

### 方案 3：Per-Consumer Queue ⭐⭐⭐⭐⭐

**重新设计**：

```
Producer 1 ──┐
Producer 2 ──┼──→ Shared Queue ──┐
Producer 3 ──┘                   ├──→ Consumer 1 Queue → Consumer 1
                                 ├──→ Consumer 2 Queue → Consumer 2
                                 └──→ Consumer 3 Queue → Consumer 3
```

**特点**：
- Producer 端：仍然零竞争
- Consumer 端：每个 consumer 独占 queue
- 中间层：负载均衡（轮询或 work stealing）

**优点**：
- 完全无竞争
- 可扩展性好
- 符合规范

**缺点**：
- 架构变化大
- 需要重新实现
